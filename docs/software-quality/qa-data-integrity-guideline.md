# 데이터 정합성 점검 항목

데이터가 언제나 업무 규칙에 부합하는 상태로 유지되는 정도를 뜻한다.

**이 문서는 판정용이다.** 항목과 판정 기준만 담고, 왜 그 기준인지와 예시 코드는
[qa-data-integrity-rationale.md](./qa-data-integrity-rationale.md) 에 있다.

"한정 자원" 은 동시에 여러 요청이 줄여 나가는 유한한 수량을 뜻한다.
재고, 좌석, 쿠폰 발급 수, API 크레딧, 계좌 잔액이 모두 같은 구조다.

## 1. 잠금 전략

점검 항목
* `[코드]` `DI-2-01` 갱신 손실 가능성이 있는 흐름에 잠금을 적용했는가
  조회한 뒤 수정하면 두 요청이 같은 값을 읽고 나중 저장이 앞선 저장을 덮어쓴다.
* `[설계]` `DI-2-02` 충돌 빈도에 맞는 잠금 방식을 골랐는가
  충돌률은 낙관적 잠금 예외 건수를 전체 갱신 시도로 나눈 값이다. 측정 없이 고르면 근거가 없다.
* `[코드]` `DI-2-03` 잠금 획득 순서가 일정해 교착 상태(deadlock)를 유발하지 않는가
* `[코드]` `DI-2-04` 낙관적 잠금 실패 시의 처리(재시도 또는 안내)가 정의되어 있는가
  예외만 던지고 끝내면 사용자에게는 이유 없는 실패로 보인다.

판정 기준 (등급 C. 근거 없음. 실제 충돌률을 측정한 뒤 확정한다)

| 충돌률 | 권장 방식 | 정한 이유 |
|--------|-----------|-----------|
| 1% 미만 | 낙관적 잠금 | 실패가 드물어 재시도 비용이 낮다 |
| 1~10% | 낙관적 잠금 + 재시도 3회 | 재시도로 대부분 흡수된다 |
| 10% 초과 | 비관적 잠금 또는 원자적 갱신 | 재시도가 오히려 부하를 키운다 |
| 단일 행 집중 | 원자적 UPDATE 또는 큐 직렬화 | 자원 하나에 요청이 몰리는 경우 |

| 항목 | 값 | 등급 |
|------|-----|------|
| `innodb_lock_wait_timeout` 기본값 | 50초 | B |
| `innodb_lock_wait_timeout` 제안값 | 5초 | C |
| 잠금 보유 시간 | 100ms 이하 | C |
| 교착 발생 | 일 1건 초과 시 조사 | C |

교착과 잠금 대기 초과는 바쁜 서버에서 정상적으로 발생한다.
"교착 0건" 을 목표로 삼지 않고 발생 빈도의 추세를 본다.

원자적 갱신을 쓸 때는 **영향받은 행 수를 반드시 확인**한다. 0이면 실패로 처리한다.

## 2. DB 제약

버그, 배치, 수동 SQL은 애플리케이션 검증을 우회한다. DB 제약이 최종 방어선이다.

점검 항목
* `[설계]` `DI-3-01` 유일성이 필요한 값에 UNIQUE 제약이 있는가
* `[설계]` `DI-3-02` 값 범위 규칙이 CHECK 제약으로도 표현되어 있는가
  MySQL 8.4 는 CHECK 를 실제로 강제한다. 8.0.16 이전에는 파싱만 하고 무시했다.
* `[설계]` `DI-3-03` 참조 무결성이 필요한 곳에 외래 키가 있는가
* `[설계]` `DI-3-04` NOT NULL이 필요한 컬럼에 지정되어 있는가
* `[코드]` `DI-3-05` 두 외래 키가 같은 조상을 가리켜야 한다면 그 조합을 검증하는가
  각각의 외래 키가 유효해도 조합이 틀릴 수 있다. 조상까지 올라가 비교해야 해서 CHECK 로 표현할 수 없다.
* `[코드]` `DI-3-06` 자식 행 합계가 부모의 상한을 넘지 않도록 잠그고 검사하는가
  행 하나씩은 유효한데 합계가 넘는 경우다. 읽고 더한 뒤 쓰는 사이에 다른 트랜잭션이 끼므로 잠금이 함께 필요하다.

판정 기준 (등급 C. 근거 없음)

| 규칙 유형 | DB 제약으로 표현 |
|-----------|------------------|
| 값 범위 | CHECK 필수 |
| 유일성 | UNIQUE 필수 |
| 필수 값 | NOT NULL 필수 |
| 참조 관계 | 외래 키 권장 |
| 상태 전이 규칙 | 애플리케이션에서 |
| 두 참조의 조합 | **애플리케이션에서.** 조상까지 올라가야 한다 |
| 여러 행의 합계 | **애플리케이션에서.** 잠금이 함께 필요하다 |

마지막 셋은 표현이 어려운 것이 아니라 **CHECK 가 자기 행만 볼 수 있어 원리적으로 불가능하다.**

## 3. 트랜잭션 경계

점검 항목
* `[코드]` `DI-4-01` 트랜잭션 범위가 비즈니스 단위와 일치하는가
* `[코드]` `DI-4-02` 트랜잭션 안에서 외부 API를 호출하지 않는가
  외부가 느리면 그동안 DB 커넥션과 락을 점유한다. 호출을 트랜잭션 밖으로 빼고 상태로 잇는다.
* `[코드]` `DI-4-03` 트랜잭션이 필요 이상으로 길지 않은가

checked 예외의 롤백 동작은 신뢰성 문서의 `REL-4-02` 가 소유한다.

판정 기준 (등급 C. 근거 없음)

| 항목 | 기준 | 조치 |
|------|------|------|
| 트랜잭션 지속 시간 | 100ms 이하 | 초과 시 범위 재검토 |
| 트랜잭션 지속 시간 상한 | 1초 | 초과는 차단 대상. 배치는 별도 기준 |
| 트랜잭션 내 외부 호출 | 0건 | 예외 없음 |
| 트랜잭션 내 갱신 행 수 | 1000행 이하 | 초과 시 청크 분할 |

## 4. 격리 수준

MySQL 8.4 InnoDB 기본은 REPEATABLE READ 다.

| 격리 수준 | 방지되는 이상 현상 |
|-----------|--------------------|
| READ UNCOMMITTED | 없음 |
| READ COMMITTED | 더티 리드 |
| REPEATABLE READ | 더티 리드, 반복 불가능 읽기 |
| SERIALIZABLE | 위 전부와 팬텀 리드 |

**격리 수준은 갱신 손실을 자동으로 막아 주지 않는다.**
읽고 계산해서 쓰는 흐름은 격리 수준과 무관하게 잠금이나 원자적 갱신이 필요하다.

## 5. 분산 환경

점검 항목
* `[설계]` `DI-6-01` 서비스 간 작업에 보상 트랜잭션이 정의되어 있는가
* `[코드]` `DI-6-02` 이벤트 발행과 DB 커밋이 원자적인가
  아웃박스 패턴은 이벤트를 같은 트랜잭션에서 테이블에 저장하고 별도 프로세스가 발행한다.
* `[코드]` `DI-6-03` 소비자가 중복 수신에 대비해 멱등한가
  메시지는 최소 한 번 전달이 일반적이라 소비자가 반드시 멱등해야 한다.
* `[인프라]` `DI-6-04` 처리 실패한 메시지가 유실되지 않고 격리되는가 (DLQ)

판정 기준 (등급 C. 근거 없음)

| 항목 | 시작값 |
|------|--------|
| 아웃박스 발행 지연 | 5초 이내 |
| 아웃박스 미발행 적체 | 100건 초과 시 경보 |
| 메시지 재시도 | 3회 후 DLQ 이동 |
| DLQ 적체 | 1건이라도 있으면 확인 대상 |

## 6. 정합성 검증

점검 항목
* `[프로세스]` `DI-7-01` 주기적 정합성 검사가 실행되는가
  탐지 없이 운영하면 몇 달 뒤 정산 시점에 원인 불명의 차이를 만난다.
* `[인프라]` `DI-7-02` 어긋남을 발견했을 때 알림이 가는가
* `[프로세스]` `DI-7-03` 정정 절차가 기록으로 남는가
  원인을 모른 채 값만 맞추면 같은 문제가 반복되고 다음에는 탐지도 늦어진다.
* `[설계]` `DI-7-04` 검사 대상과 허용 오차가 정의되어 있는가

검사 대상과 주기 (예시값)

| 검사 유형 | 주기 | 허용 오차 | 초과 시 |
|-----------|------|-----------|---------|
| 집계값 vs 원본 합계 | 1시간 | 0 | 경보 |
| 우리 기록 vs 외부 시스템 기록 | 일 1회 | 0 | 즉시 경보 |
| 양방향 금액 대사 | 일 1회 | 0 | 즉시 경보 |
| 상태 이력의 연속성 | 일 1회 | 0 | 조사 |
| 고아 데이터 | 일 1회 | 0 | 조사 |

금전이 걸린 항목은 허용 오차가 없다.
금전을 다루지 않는 서비스라면 그 자리에 핵심 불변식을 넣는다.
