# 관측 가능성 점검 항목

시스템의 외부 출력만으로 내부 상태를 파악할 수 있는 정도를 뜻한다.

**이 문서는 판정용이다.** 항목과 판정 기준만 담고, 왜 그 기준인지와 예시 코드는
[qa-observability-rationale.md](./qa-observability-rationale.md) 에 있다.

판정의 기준은 하나다. **새로 발생한 문제를 코드 배포 없이 진단할 수 있는가.**

## 1. 로그

점검 항목
* `[인프라]` `OBS-3-01` 구조화된 형식(JSON)으로 남는가
  문자열 연결 로그는 검색과 집계가 불가능하다.
* `[코드]` `OBS-3-02` 요청 단위 상관관계 ID가 모든 로그에 붙는가
  MDC 를 쓰면 `MDC.clear()` 를 빠뜨렸을 때 다음 요청이 이전 traceId 를 이어받는다.
* `[코드]` `OBS-3-03` 로그 레벨이 의미에 맞게 쓰이는가
  모든 예외를 ERROR 로 남기면 알림이 무의미해진다. 사용자 입력 오류는 WARN 이하가 맞다.
* `[코드]` `OBS-3-04` 개인정보와 인증 토큰이 남지 않는가
* `[설계]` `OBS-3-05` 로그가 성능과 비용에 영향을 줄 만큼 과도하지 않은가
  비동기 appender 에 `neverBlock` 을 켜지 않으면 로그 수집이 느려질 때 요청 스레드가 함께 멈춘다.
* `[인프라]` `OBS-3-06` 보존 기간과 접근 권한이 정의되어 있는가

판정 기준 (전부 등급 C. 근거 없음)

| 항목 | 예시값 | 정한 이유 |
|------|--------|-----------|
| 요청당 INFO 로그 | 3줄 이하 | 상태 변화만 남긴다 |
| 단일 로그 길이 | 2KB 이하 | 응답 본문 전체를 찍지 않는다 |
| 로그로 인한 응답시간 증가 | p99의 5% 이하 | 초과 시 비동기 appender 검토 |
| 보존 기간 | 운영 로그 30일, 감사 로그 1년 | 조사 기간과 비용의 절충 |

로그 레벨 기준

| 레벨 | 기준 | 알림 |
|------|------|------|
| ERROR | 사람이 개입해야 하는 실패 | 즉시 |
| WARN | 자동 복구됐지만 반복되면 문제인 상황 | 임계치 초과 시 |
| INFO | 상태 변화 기록 | 없음 |
| DEBUG | 개발과 조사용. 운영에서는 기본 비활성 | 없음 |

## 2. 메트릭

점검 항목
* `[인프라]` `OBS-4-01` RED 또는 USE 관점의 기본 지표를 노출하는가
* `[코드]` `OBS-4-02` 기술 지표뿐 아니라 비즈니스 지표를 함께 수집하는가
  CPU 와 응답시간이 정상인데 핵심 기능이 전부 실패하고 있을 수 있다.
* `[코드]` `OBS-4-03` 태그(label) 카디널리티가 폭발하지 않는가
  ID, 이메일, URL 원문을 태그로 넣으면 시계열이 무한히 늘어나 수집기가 죽는다.
* `[인프라]` `OBS-4-04` 수집 주기와 보존 기간이 정의되어 있는가

| 관점 | 지표 | 대상 |
|------|------|------|
| RED | Rate, Errors, Duration | 요청 처리 서비스 |
| USE | Utilization, Saturation, Errors | 자원(CPU, 커넥션풀, 큐) |

판정 기준 (전부 등급 C. 근거 없음)

| 항목 | 예시값 | 정한 이유 |
|------|--------|-----------|
| 메트릭 하나당 시계열 수 | 1000개 이하 | 태그 조합의 곱으로 늘어난다 |
| 태그 값 종류 | 항목당 50개 이하 | ID, 이메일, URL 원문은 태그 금지 |
| 수집 주기 | 15초 | 급변 감지와 저장 비용의 절충 |
| 보존 기간 | 원본 15일, 다운샘플링 후 1년 | 추세 비교에 필요한 기간 |

## 3. 분산 추적

점검 항목
* `[인프라]` `OBS-5-01` 서비스 간 호출에 추적 컨텍스트가 전파되는가
* `[인프라]` `OBS-5-02` DB 쿼리와 외부 호출이 스팬으로 기록되는가
  전체 2초 중 1.8초가 특정 외부 호출이었다는 사실은 스팬 단위로 봐야 드러난다.
* `[인프라]` `OBS-5-03` 샘플링 정책이 정의되어 있는가
* `[코드]` `OBS-5-04` 비동기 실행에서 추적 컨텍스트가 끊기지 않는가

판정 기준 (등급 C. 근거 없음)

| 대상 | 샘플링 비율 | 근거 |
|------|-------------|------|
| 오류 응답 | 100% | 조사 대상은 빠짐없이 남긴다 |
| 느린 요청 (p99 초과) | 100% | 성능 문제의 근거 자료 |
| 핵심 거래 경로 | 10% | 정상 흐름의 기준선 확보 |
| 일반 조회 | 1% | 비용 통제 |

## 4. SLO와 알림

점검 항목
* `[설계]` `OBS-6-01` 주요 기능에 SLI와 SLO가 숫자로 정의되어 있는가
  "핵심 조회 API 는 p99 200ms 이하를 30일 기준 99.9% 충족한다" 형태여야 한다.
* `[인프라]` `OBS-6-02` 알림이 원인이 아니라 증상(사용자 영향) 기준인가
  "CPU 80% 초과" 는 문제가 아닐 수 있고 "핵심 API 오류율 5% 초과" 는 확실한 문제다.
* `[프로세스]` `OBS-6-03` 알림에 대응 절차가 연결되어 있는가
  `runbook` 링크가 없는 알림은 만들지 않는다. 무엇을 해야 할지 모르는 알림은 소음이다.
* `[프로세스]` `OBS-6-04` 무시되는 알림이 쌓이고 있지 않은가
  알림 목록은 늘어나기만 하고 줄지 않는다. 분기 1회 정리 절차가 없으면 아무도 보지 않게 된다.

경보 임계 (등급 B. Google SRE Workbook)

| 소진 속도 | 긴 구간 | 짧은 구간 | 대응 |
|-----------|---------|-----------|------|
| 14.4배 | 1시간 | 5분 | 즉시 호출(page) |
| 6배 | 6시간 | 30분 | 즉시 호출(page) |
| 1배 | 3일 | 6시간 | 티켓 |

두 구간이 동시에 임계를 넘을 때만 발화시켜 오탐을 줄인다.
**요청량이 적은 서비스에서는 이 방식이 과민하게 동작한다.** 시간당 10건 규모면 별도 방식이 필요하다.

예시값 (등급 C. 근거 없음)

| 항목 | 예시값 | 조치 |
|------|--------|------|
| 알림 정확도 | 70% 이상 | 미달 시 임계치 재조정 |
| 주간 알림 건수 | 담당자당 10건 이하 | 초과 시 통합하거나 임계치 상향 |
| 미대응 알림 비율 | 10% 이하 | 초과한 알림은 삭제 대상 |

## 5. 진단 가능성

점검 항목
* `[코드]` `OBS-7-01` 예외에 원인 추적에 필요한 식별자가 포함되는가
  "요청 처리 실패" 만으로는 무엇이 실패했는지 알 수 없다.
* `[코드]` `OBS-7-02` 외부 시스템 응답 코드가 원문 그대로 기록되는가
* `[인프라]` `OBS-7-03` 배포 버전이 로그와 메트릭에 태그로 남는가
  없으면 "이번 배포 이후 느려졌는가" 에 답할 수 없다.

## 6. 측정 지표

| 지표 | 의미 | 목표 (예시값) |
|------|------|---------------|
| MTTD | 장애 발생부터 인지까지 | 5분 이하 |
| MTTR | 인지부터 복구까지 | RTO 이내 |
| 알림 정확도 | 실제 조치가 필요했던 비율 | 70% 이상 |
| 무계측 구간 비율 | 메트릭이나 추적이 없는 경로 | 핵심 경로 0% |
| 코드 변경 없이 진단된 장애 비율 | 관측 가능성의 실효성 | 80% 이상 |
