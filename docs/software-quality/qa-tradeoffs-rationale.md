# 품질 속성 충돌 점검 항목의 근거

판정용 항목 목록은 [qa-tradeoffs-guideline.md](./qa-tradeoffs-guideline.md) 에 있다.
이 문서는 왜 그 기준인지와 예시를 담는다.

품질 속성은 동시에 최대화할 수 없다.
설계란 이 충돌을 인지하고 어느 쪽을 얼마나 포기할지 명시적으로 고르는 일이다.

가장 위험한 상태는 트레이드오프가 있다는 사실 자체를 모르고 한쪽만 최적화하는 것이다.

> **수치에는 근거 등급이 표시되어 있다.**
> A는 산술로 도출된 값, B는 출처가 있는 값(링크 표기), C는 근거 없이 정한 예시값이다.
> C로 표시된 값은 그대로 채택하지 말고 측정 후 팀이 확정한다.
> 등급 정의는 quality-attributes.md의 "판정 기준 수치의 성격"을 참고한다.

## 1. 주요 충돌 관계

| 충돌 | 내용 | 판단 기준 |
|------|------|-----------|
| 성능 <-> 정합성 | 캐시와 비정규화는 빠르지만 진실이 둘이 되어 어긋난다 | 그 경로에 근사값이 허용되는가 |
| 성능 <-> 유지보수성 | 최적화된 쿼리와 수동 매핑은 읽기 어렵다 | 병목이 실제로 측정되었는가 |
| 가용성 <-> 정합성 | 분산 환경에서 분단 시 둘 중 하나를 포기해야 한다 | 잘못된 데이터와 응답 실패 중 무엇이 더 나쁜가 |
| 보안 <-> 성능 | 암호화, 감사 로그, 검증은 모두 비용이다 | 데이터 민감도 등급 |
| 보안 <-> 사용성 | 인증 강화는 이탈을 늘린다 | 사고 발생 시 손실 규모 |
| 유연성 <-> 단순성 | 과도한 추상화는 지금의 가독성을 판다 | 교체 가능성이 실재하는가 |
| 확장성 <-> 정합성 | 무상태화와 분산은 강한 일관성을 어렵게 한다 | 최종 일관성으로 표현 가능한 업무인가 |
| 개발 속도 <-> 모든 속성 | 초기 속도를 위해 진 빚은 이자가 붙는다 | 되돌리기 쉬운 결정인가 |

## 2. 성능과 정합성

가장 자주 마주치는 충돌이다.

한정 자원의 잔여 수량을 예로 들면, 같은 데이터가 두 경로에서 전혀 다른 요구를 받는다.

| 경로 | 요구 | 방식 |
|------|------|------|
| 목록에 잔여 수량 표시 | 빨라야 함. 약간 낡아도 됨 | 집계 캐시, 근사값 허용 |
| 그 수량을 근거로 차감 | 정확해야 함. 조금 느려도 됨 | 실시간 조회 + 잠금 |

여기서 "한정 자원"은 재고, 좌석, 쿠폰, 크레딧처럼 동시에 여러 요청이 줄여 나가는 유한한 수량을 뜻한다.

핵심 원칙은 **경로를 분리하는 것**이다.
하나의 방식으로 두 요구를 모두 만족시키려 하면 둘 다 어중간해진다.

비정규화는 정확성 비용(진실이 둘이 되어 어긋나는 위험)을 먼저 치른다.
따라서 존재하지 않는 병목을 위해 실재하는 버그 위험을 미리 떠안지 않는다.
원본 행을 실시간으로 집계하는 방식으로 시작하고, 병목이 관측된 뒤 단계적으로 확장한다.

## 3. 가용성과 정합성

네트워크 분단 상황에서 둘 다 만족시킬 수 없다는 것이 CAP의 요지다.
실무에서 이 선택은 기능 단위로 다르게 내린다.

| 기능 유형 | 선택 | 이유 |
|-----------|------|------|
| 금전 처리, 한정 자원 차감 | 정합성 | 틀린 데이터가 응답 실패보다 나쁘다 |
| 목록 조회, 추천, 검색 | 가용성 | 조금 낡아도 보여 주는 편이 낫다 |
| 조회수, 반응 수 같은 통계 | 가용성 | 정확할 필요가 없다 |

전체 시스템을 한 가지로 정할 필요는 없다.
"이 API는 어느 쪽인가"를 기능별로 결정하는 편이 현실적이다.

## 4. 보안과 성능, 사용성

보안 조치는 예외 없이 비용을 수반한다.

| 조치 | 비용 |
|------|------|
| 저장 데이터 암호화 | 쓰기 지연, 해당 컬럼 인덱스 검색 제약 |
| 감사 로그 | 쓰기 증가, 저장 비용 |
| 모든 요청 인가 검증 | 조회당 추가 쿼리 |
| 다단계 인증 | 사용자 이탈 |

판단 기준은 데이터 민감도와 사고 시 손실 규모다.
신원 확인용 고유 식별자와 단순 조회 이력에 같은 수준의 보호를 적용할 이유가 없다.
반대로 모든 데이터를 같은 등급으로 낮추면 사고가 난다.

데이터를 등급으로 나누고 등급별 조치를 정하는 것이 실무적인 접근이다.

## 5. 유연성과 단순성

추상화는 미래의 교체 가능성을 사고 현재의 가독성을 판다.

점검 항목
* `[설계]` `TRD-5-01` 이 확장점을 쓸 두 번째 구현이 실제로 예상되는가
* `[설계]` `TRD-5-02` 지금 없는 요구를 위해 인터페이스를 만들고 있지 않은가
* `[코드]` `TRD-5-03` 추상화 계층을 하나 더 거쳐야 코드를 이해할 수 있게 되지 않는가

외부 연동처럼 실제로 교체하거나 여러 공급자를 병행 운영할 가능성이 높은 곳은 추상화가 값을 한다.
반면 하나뿐인 구현체를 위한 인터페이스는 파일 수만 늘리고 추적만 어렵게 만든다.

되돌리기 쉬운 결정은 나중에 해도 된다.
인터페이스 추출은 언제든 할 수 있지만, 잘못 나눈 서비스 경계를 되돌리는 것은 훨씬 비싸다.

## 6. 기준 수치를 조정하는 절차

각 문서의 판정 기준은 출발점이다. 조정 자체는 정상이지만, 조정 방식에 규칙이 없으면 기준이 유명무실해진다.

점검 항목
* `[프로세스]` `TRD-6-01` 기준을 조정할 때 이유와 근거 데이터를 남기는가
* `[프로세스]` `TRD-6-02` 완화한 기준을 재검토하는 시점이 정해져 있는가
* `[프로세스]` `TRD-6-03` 계속 위반되는데 방치된 기준이 없는가

```
기준 조정 절차

1. 조정 사유 분류
   - 측정 결과 현재 기준이 과도하게 엄격함 -> 완화 검토
   - 사고를 겪어 기준이 부족함이 드러남 -> 강화
   - 서비스 특성상 처음부터 맞지 않음 -> 재설정
2. 완화하는 경우 근거 데이터를 첨부한다
   "3개월간 이 기준 위반 42건 중 실제 문제로 이어진 건 0건"
3. 조정 결과를 기록한다: 항목, 이전값, 새 값, 사유, 결정자, 날짜
4. 완화한 기준은 6개월 뒤 재검토 일정을 잡는다
5. 6개월간 한 번도 지켜지지 않았고 조정도 하지 않은 기준은 삭제한다
```

지켜지지 않는 기준을 남겨 두면 나머지 기준의 신뢰도까지 떨어진다.
"어차피 다 못 지키는 목록"이 되는 순간 아무도 보지 않는다.

## 7. 결정 순서

1. **되돌리기 어려운 것부터 정한다.** 데이터 모델, 서비스 경계, API 계약은 되돌리기 어렵다. 캐시 도입, 인덱스 추가, 라이브러리 교체는 쉽다.
2. **기능별로 목표를 다르게 잡는다.** 핵심 거래 API와 내부 통계 대시보드에 같은 가용성과 지연 목표를 요구할 이유가 없다.
3. **숫자로 정한다.** "빨라야 한다"가 아니라 "p99 200ms 이하"여야 검증할 수 있다.
4. **측정 후 최적화한다.** 추측 기반 최적화는 유지보수성만 잃는다.
5. **기록한다.** 어떤 대안을 왜 버렸는지가 6개월 뒤 가장 필요한 정보다.

## 8. 결정 기록 양식

코드는 무엇을 하는지 말하지만 왜 그렇게 했는지는 말해 주지 않는다.
설계 판단은 다음 형태로 남긴다.

```
## D-012 잔여 수량 조회를 실시간 집계로 유지

상태: 채택
날짜: 2026-07-30

### 맥락
목록 화면에서 자원별 잔여 수량을 노출해야 한다.
잔여 수량은 단일 컬럼이 아니라 여러 할당 행의 합계이며, 만료되지 않은 행만 세야 한다.
현재 자원 수는 수천 개, 자원당 활성 할당 행은 3~10개다.

### 선택지
1. 조회 시점에 원본 행을 실시간 집계 (IN + GROUP BY)
2. 부모 테이블에 집계값 컬럼을 비정규화
3. 캐시 계층 도입

### 결정
1번을 채택한다.

### 근거
현재 규모에서 커버링 인덱스를 태운 집계 한 번이면 수 ms로 처리된다.
2번은 같은 사실을 두 곳에 저장하게 되어 동기화 버그 위험을 지금 떠안는다.
3번은 아직 측정된 병목이 없다.

### 포기한 것
목록 조회가 할당 테이블 구조에 의존하므로, 자원당 행 수가 크게 늘면 재검토가 필요하다.

### 재검토 조건
목록 API p99가 300ms를 넘거나, 자원당 평균 활성 행이 50개를 넘을 때
```

재검토 조건을 함께 적는 것이 중요하다.
그것이 없으면 결정이 영구 규칙처럼 굳어져, 상황이 바뀌어도 아무도 다시 열어 보지 않는다.
