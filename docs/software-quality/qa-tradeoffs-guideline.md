# 품질 속성 충돌 점검 항목

품질 속성은 서로 충돌한다. 하나를 올리면 다른 하나가 내려간다.

**이 문서는 판정용이다.** 항목과 판정 기준만 담고, 각 충돌의 배경과 결정 사례는
[qa-tradeoffs-rationale.md](./qa-tradeoffs-rationale.md) 에 있다.

## 1. 주요 충돌 관계

| 충돌 | 내용 | 판단 기준 |
|------|------|-----------|
| 성능 <-> 정합성 | 캐시와 비정규화는 빠르지만 진실이 둘이 되어 어긋난다 | 그 경로에 근사값이 허용되는가 |
| 성능 <-> 유지보수성 | 최적화된 쿼리와 수동 매핑은 읽기 어렵다 | 병목이 실제로 측정되었는가 |
| 가용성 <-> 정합성 | 분단 시 둘 중 하나를 포기해야 한다 | 잘못된 데이터와 응답 실패 중 무엇이 더 나쁜가 |
| 보안 <-> 성능 | 암호화, 감사 로그, 검증은 모두 비용이다 | 데이터 민감도 등급 |
| 보안 <-> 사용성 | 인증 강화는 이탈을 늘린다 | 사고 발생 시 손실 규모 |
| 유연성 <-> 단순성 | 과도한 추상화는 지금의 가독성을 판다 | 교체 가능성이 실재하는가 |
| 확장성 <-> 정합성 | 무상태화와 분산은 강한 일관성을 어렵게 한다 | 최종 일관성으로 표현 가능한가 |
| 개발 속도 <-> 모든 속성 | 초기 속도를 위해 진 빚은 이자가 붙는다 | 되돌리기 쉬운 결정인가 |

## 2. 유연성과 단순성

추상화는 미래의 교체 가능성을 사고 현재의 가독성을 판다.

점검 항목
* `[설계]` `TRD-5-01` 이 확장점을 쓸 두 번째 구현이 실제로 예상되는가
  외부 연동처럼 교체나 병행 운영 가능성이 높은 곳은 추상화가 값을 한다.
* `[설계]` `TRD-5-02` 지금 없는 요구를 위해 인터페이스를 만들고 있지 않은가
  하나뿐인 구현체를 위한 인터페이스는 파일 수만 늘리고 추적만 어렵게 만든다.
* `[코드]` `TRD-5-03` 추상화 계층을 하나 더 거쳐야 코드를 이해할 수 있게 되지 않는가

**되돌리기 쉬운 결정은 나중에 해도 된다.**
인터페이스 추출은 언제든 할 수 있지만 잘못 나눈 서비스 경계를 되돌리는 것은 훨씬 비싸다.

## 3. 기준 수치 조정

각 문서의 판정 기준은 출발점이다. 조정 자체는 정상이지만 방식에 규칙이 없으면 기준이 유명무실해진다.

점검 항목
* `[프로세스]` `TRD-6-01` 기준을 조정할 때 이유와 근거 데이터를 남기는가
  완화하려면 "3개월간 위반 42건 중 실제 문제로 이어진 건 0건" 같은 데이터를 첨부한다.
* `[프로세스]` `TRD-6-02` 완화한 기준을 재검토하는 시점이 정해져 있는가
  완화한 기준은 6개월 뒤 재검토 일정을 잡는다.
* `[프로세스]` `TRD-6-03` 계속 위반되는데 방치된 기준이 없는가
  6개월간 한 번도 지켜지지 않았고 조정도 하지 않은 기준은 삭제한다.

지켜지지 않는 기준을 남겨 두면 나머지 기준의 신뢰도까지 떨어진다.

## 4. 결정 순서

1. **되돌리기 어려운 것부터 정한다.** 데이터 모델, 서비스 경계, API 계약은 되돌리기 어렵다.
2. **기능별로 목표를 다르게 잡는다.** 핵심 거래와 내부 통계에 같은 목표를 요구할 이유가 없다.
3. **숫자로 정한다.** "빨라야 한다" 가 아니라 "p99 200ms 이하" 여야 검증할 수 있다.
4. **측정 후 최적화한다.** 추측 기반 최적화는 유지보수성만 잃는다.
5. **기록한다.** 어떤 대안을 왜 버렸는지가 6개월 뒤 가장 필요한 정보다.
