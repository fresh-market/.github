# 장애 대응 점검 항목의 근거

판정용 항목 목록은 [qa-incident-response-guideline.md](./qa-incident-response-guideline.md) 에 있다.
이 문서는 왜 그 기준인지와 예시를 담는다.

서버나 의존 시스템이 실제로 죽었을 때 **사람이 무엇을 하는가**를 다룬다.

신뢰성 문서([qa-reliability-rationale.md](./qa-reliability-rationale.md))가 "시스템이 복구 가능한 성질을 갖추었는가"를 설계 관점에서 다룬다면, 이 문서는 "지금 죽었다, 다음 단계는 무엇인가"를 실행 순서로 다룬다.
RPO와 RTO를 정하는 것은 신뢰성 문서, 그 RTO 안에 실제로 복구해 내는 것은 이 문서의 몫이다.

## 0. 이 문서를 쓰는 방식

장애 한복판에서 읽는 문서는 설계 검토용 문서와 형식이 달라야 한다.

* 판단이 필요한 지점과 기계적으로 실행할 지점을 구분한다.
* 순서대로 실행 가능해야 한다. 배경 설명은 뒤로 뺀다.
* 위험한 조작에는 되돌릴 수 없다는 표시를 남긴다.

> **수치에는 근거 등급이 표시되어 있다.**
> A는 산술로 도출된 값, B는 출처가 있는 값(링크 표기), C는 근거 없이 정한 예시값이다.
> C로 표시된 값은 그대로 채택하지 말고 팀이 확정한다.

## 1. 심각도 등급

등급을 먼저 정해야 누구를 부를지, 어디까지 감수할지가 정해진다.

판정 기준 (등급 C. 근거 없음. 서비스 규모에 맞게 재정의한다)

| 등급 | 정의 | 대응 | 통지 |
|------|------|------|------|
| SEV1 | 핵심 기능 전면 불가. 금전 사고 또는 데이터 손실 발생 | 즉시 호출, 역할 분리 | 경영진 포함 전사 |
| SEV2 | 핵심 기능 일부 불가 또는 심각한 성능 저하 | 즉시 호출 | 관련 팀 |
| SEV3 | 부가 기능 장애. 우회 수단 있음 | 업무 시간 내 대응 | 담당 팀 |
| SEV4 | 사용자 영향 없음. 이중화로 흡수됨 | 티켓 | 없음 |

점검 항목
* `[프로세스]` `INC-1-01` 등급 판정 기준이 문서화되어 있고 당직자가 즉시 참조 가능한가
* `[프로세스]` `INC-1-02` 등급을 올리는 것이 벌점이 되지 않는가
* `[프로세스]` `INC-1-03` 등급별로 누구를 부르는지 명단이 최신인가

등급은 **의심스러우면 올린다**. 나중에 내리는 비용은 작고, 늦게 올리는 비용은 크다.
등급을 올렸다는 이유로 문책하면 아무도 올리지 않게 되고, 그 순간 이 기준은 무의미해진다.

## 2. 역할 분리

판정 기준 (등급 B. Google SRE의 인시던트 관리 체계)

출처: https://sre.google/sre-book/managing-incidents/ , https://sre.google/workbook/incident-response/

출처는 조율(Coordinate), 소통(Communicate), 통제(Control)를 인시던트 관리의 세 축으로 두고 세 역할을 정의한다.

| 역할 | 하는 일 | 하지 않는 일 |
|------|---------|--------------|
| 지휘자 (Incident Commander) | 전체 상황 파악, 판단, 역할 위임 | 직접 디버깅하지 않는다 |
| 실행자 (Operations Lead) | 조사와 완화 조치 실행 | 상태 공유에 시간을 쓰지 않는다 |
| 소통자 (Communications Lead) | 상태 공유, 외부 문의 대응, 기록 | 시스템을 건드리지 않는다 |

출처의 핵심 규칙 세 가지를 그대로 따른다.

1. **위임되지 않은 역할은 지휘자가 갖는다.** 처음에는 장애를 선언한 사람이 지휘자가 되고, 필요에 따라 위임한다.
2. **시스템을 변경하는 것은 실행자뿐이다.** 여러 사람이 동시에 손대면 무엇이 원인이고 무엇이 조치였는지 사후에 구분할 수 없다.
3. **지휘 인계는 명시적으로 한다.** "이제 당신이 지휘자입니다"라고 말하고 상대의 확인을 받은 뒤에 자리를 뜬다. 인계 사실은 참여자 전원에게 공유한다.

작은 장애에서는 한 사람이 세 역할을 겸해도 된다.
다만 SEV1과 SEV2에서는 반드시 분리한다. 조사하는 사람이 상태 공유까지 맡으면 조사가 멈춘다.

점검 항목
* `[프로세스]` `INC-2-01` 장애 시작 시점에 지휘자가 누구인지 명시적으로 선언되는가
* `[프로세스]` `INC-2-02` 시스템 변경을 실행자 한 명으로 제한하는가
* `[프로세스]` `INC-2-03` 지휘 인계가 구두 확인을 거쳐 이루어지는가
* `[프로세스]` `INC-2-04` 팀원이 역할을 돌아가며 맡아 본 경험이 있는가

## 3. 초기 대응 순서

**완화가 원인 규명보다 먼저다.** 출처도 완화 우선(mitigation-first) 대응을 권한다.
원인을 다 밝힌 뒤 조치하려 하면 그동안 사용자는 계속 실패한다.

```
장애 인지 후 실행 순서

1. 선언       "장애 시작. 내가 지휘자." 채널 개설, 시각 기록
2. 등급 판정   SEV 등급을 잠정 결정. 의심스러우면 올린다
3. 영향 확인   무엇이 안 되는가. 몇 퍼센트가 영향받는가. 언제부터인가
4. 최근 변경 확인  최근 배포, 설정 변경, 외부 공지가 있었는가
                  있으면 원인 규명보다 롤백을 먼저 검토한다 (5장)
5. 완화 조치   아래 우선순위로. 원인 규명은 병행하되 완화를 막지 않는다
6. 확인       사용자 영향이 실제로 사라졌는지 지표로 확인. 로그가 아니라 지표로
7. 안정화     재발 여부를 관찰. 최소 30분 (등급 C)
8. 종료 선언   지휘자가 명시적으로 종료를 선언하고 사후 분석 일정을 잡는다
```

완화 조치의 우선순위 (등급 C)

| 순위 | 조치 | 되돌리기 |
|------|------|----------|
| 1 | 최근 배포 롤백 | 쉬움 |
| 2 | 기능 스위치로 부가 기능 차단 | 쉬움 |
| 3 | 트래픽 차단 또는 레이트 리밋 강화 | 쉬움 |
| 4 | 인스턴스 재기동 또는 증설 | 보통 |
| 5 | 페일오버 (인스턴스 교체, 복제본 승격) | 어려움 |
| 6 | 백업에서 복원 | 매우 어려움. 데이터 손실 수반 |

위에서부터 시도한다. 아래로 갈수록 되돌리기 어렵고 부작용이 크다.

점검 항목
* `[프로세스]` `INC-3-01` 완화를 원인 규명보다 먼저 시도하는 것이 합의되어 있는가
* `[인프라]` `INC-3-02` 위 1~3번 조치를 배포 없이 즉시 실행할 수 있는가
* `[프로세스]` `INC-3-03` 조치 시각과 내용이 실시간으로 기록되는가

3번까지의 조치를 배포해야만 할 수 있다면 완화 수단이 없는 것과 같다.
빌드와 배포에 걸리는 시간만큼 장애가 길어진다.

## 4. 인스턴스 장애와 페일오버

### 4.1 애플리케이션 인스턴스

무상태로 설계되어 있다면 인스턴스 하나가 죽는 것은 장애가 아니라 정상 동작의 일부다.
문제가 되는 경우는 다음 셋이다.

| 상황 | 증상 | 조치 |
|------|------|------|
| 남은 인스턴스가 부하를 못 견딤 | 연쇄 장애로 나머지도 순차 사망 | 즉시 증설 또는 트래픽 차단 |
| readiness 통과 전에 트래픽 유입 | 기동 직후 오류 급증 | readiness 조건 확인 |
| 죽은 인스턴스가 작업을 쥔 채 사망 | 스케줄러 락 점유, 큐 메시지 미확인 | 락 만료 확인, 메시지 재처리 |

점검 항목
* `[설계]` `INC-4-01` 인스턴스 하나가 죽어도 남은 인스턴스가 부하를 감당할 수 있는가
* `[인프라]` `INC-4-02` 분산 락에 만료 시간이 있어 급사한 인스턴스가 락을 영구 점유하지 않는가
* `[인프라]` `INC-4-03` 처리 중이던 메시지가 확인되지 않으면 재전달되는가

락 만료 시간이 없으면 인스턴스가 죽는 순간 그 작업은 영원히 재개되지 않는다.
스케줄러가 매시 실행이라면 사람이 개입할 때까지 계속 건너뛴다.

### 4.2 DB 복제본 승격

**이 절의 조작은 되돌릴 수 없다.** 승격 후에는 원래 소스로 되돌리는 것이 새로운 작업이 된다.

승격 전에 반드시 확인할 것

1. 소스가 정말 죽었는가. 네트워크 단절로 안 보이는 것뿐이라면 승격 시 양쪽이 모두 쓰기를 받는 상태(split brain)가 된다.
2. 복제본이 어디까지 따라왔는가. 비동기 복제라면 승격 시점 이후의 데이터는 손실된다.
3. 손실 예상 범위가 RPO 안에 들어오는가.

```sql
-- 승격 전 확인: 복제 지연과 적용 위치
SHOW REPLICA STATUS\G
-- Seconds_Behind_Source, Last_IO_Error, Last_SQL_Error 확인
-- GTID 사용 시 Retrieved_Gtid_Set 과 Executed_Gtid_Set 의 차이가 미적용분
```

```sql
-- 수신했으나 아직 적용하지 않은 트랜잭션을 끝까지 적용시킨다 (GTID 환경)
SELECT WAIT_FOR_EXECUTED_GTID_SET('<Retrieved_Gtid_Set 값>', 30);
```

```sql
-- 승격 (되돌릴 수 없음)
STOP REPLICA;
RESET REPLICA ALL;                 -- 복제 설정 제거
SET GLOBAL super_read_only = OFF;
SET GLOBAL read_only = OFF;        -- 쓰기 허용
```

승격 후 순서

1. 애플리케이션의 쓰기 대상을 새 소스로 전환한다 (설정 변경 또는 DNS 전환).
2. 다른 복제본이 있다면 새 소스를 바라보도록 재구성한다.
3. 손실 구간을 특정해 기록한다. 어떤 트랜잭션이 사라졌는지 모르면 사후 정정이 불가능하다.
4. 정합성 검증(7장)을 수행한다.

점검 항목
* `[프로세스]` `INC-4-04` 승격 절차가 문서화되어 있고 실제로 연습해 보았는가
* `[코드]` `INC-4-05` split brain을 막는 장치(펜싱, 쿼럼)가 있는가
* `[인프라]` `INC-4-06` 쓰기 대상 전환이 배포 없이 가능한가
* `[프로세스]` `INC-4-07` 손실 구간을 특정하는 방법이 정해져 있는가

절차를 연습해 본 적이 없다면 장애 상황에서 처음 해 보게 된다.
그때는 손이 떨리고, 문서에 없는 단계에서 막히고, 대개 더 큰 사고로 이어진다.

## 5. 배포 롤백 실행

최근 배포가 원인일 가능성이 있으면 원인 규명보다 롤백을 먼저 검토한다.
롤백은 되돌리기 쉬운 조치이므로, 원인이 아니었더라도 잃는 것이 적다.

```
롤백 판단 순서

1. 최근 배포 시각과 장애 시작 시각이 겹치는가
   겹치면 -> 롤백 우선 검토
2. 스키마 변경이 함께 배포되었는가
   - 없음        -> 즉시 롤백 가능
   - 있음(호환)  -> 즉시 롤백 가능. 새 컬럼은 무시되어도 무방
   - 있음(비호환) -> 롤백 불가. 앞으로 수정(roll forward)해야 한다
3. 롤백 후 확인: 오류율과 지연시간이 배포 전 수준으로 돌아왔는지 지표로 확인
4. 돌아오지 않으면 원인이 배포가 아니다. 다음 완화 조치로 넘어간다
```

점검 항목
* `[인프라]` `INC-5-01` 이전 버전으로 되돌리는 데 걸리는 시간을 알고 있는가
* `[설계]` `INC-5-02` 스키마 변경이 코드 롤백을 막고 있지 않은가
* `[프로세스]` `INC-5-03` 롤백 결정 권한이 누구에게 있는지 명확한가

스키마를 단계적으로 변경하지 않으면(추가 -> 양쪽 쓰기 -> 읽기 전환 -> 제거), 배포와 스키마가 서로를 붙들어 롤백이 불가능해진다.
그러면 장애 중에 앞으로 수정하는 수밖에 없고, 이는 압박 속에서 새 코드를 쓰는 가장 위험한 상황이다.

## 6. 재기동 후 복구

죽었던 서버가 살아나는 순간이 두 번째 위험 구간이다.
평상시 상태를 전제로 만든 시스템이 비어 있는 상태로 부하를 받는다.

| 현상 | 원인 | 대응 |
|------|------|------|
| 기동 직후 응답 지연 폭증 | 캐시가 비어 모든 요청이 원본으로 | 트래픽을 단계적으로 유입 |
| DB 커넥션 오류 급증 | 전 인스턴스가 동시에 커넥션 재수립 | 기동 시각 분산, 풀 초기화 지연 |
| 큐 적체 폭발적 소비 | 쌓인 메시지를 한꺼번에 처리 | 소비 속도 제한 |
| 클라이언트 재시도 몰림 | 복구를 감지한 클라이언트가 동시 재시도 | 서버 측 레이트 리밋 유지 |

점검 항목
* `[인프라]` `INC-6-01` 기동 후 트래픽을 단계적으로 유입시킬 수 있는가
* `[인프라]` `INC-6-02` 큐 소비 속도에 상한이 있는가
* `[설계]` `INC-6-03` 캐시가 빈 상태에서 원본이 감당 가능한 부하인가
* `[인프라]` `INC-6-04` 복구 직후 레이트 리밋을 평소보다 강하게 걸 수 있는가

```yaml
# 개선: 기동 직후 준비되지 않은 상태로 트래픽을 받지 않도록 조건을 좁힌다
management:
  endpoint:
    health:
      probes:
        enabled: true
      group:
        readiness:
          include: db, redis, diskSpace
```

캐시가 빈 상태의 부하를 원본이 못 견디면, 복구가 곧바로 두 번째 장애가 된다.
이 경우 사전 적재(warm-up)로 캐시를 채운 뒤 트래픽을 열어야 한다.

## 7. 부분 복구 후 정합성 검증

서비스가 살아났다고 끝이 아니다. 장애 구간에 어긋난 데이터가 남아 있을 수 있다.

확인 순서 (등급 C)

```
1. 장애 구간을 시각으로 특정한다 (시작, 종료)
2. 그 구간에 생성 또는 변경된 데이터를 대상으로 검증한다
   - 상태가 중간에 멈춘 건 (PENDING, PROCESSING 상태로 방치)
   - 외부 시스템과 대사가 맞지 않는 건 (결제, 배송)
   - 중복 처리된 건 (재시도로 인한 이중 실행)
   - 미확정 상태로 남은 외부 호출
3. 자동 정정 가능한 것과 사람이 판단해야 하는 것을 분리한다
4. 정정 내역을 기록한다: 실행자, 시각, 대상, 실행한 SQL, 영향 행 수, 사유
5. 손실이 확정된 데이터는 별도로 목록화한다. 복구 불가능한 것을 복구된 것처럼 두지 않는다
```

아래는 유형별 예시다. 테이블과 상태값은 서비스의 도메인에 맞게 바꾼다.

```sql
-- 유형 1: 장애 구간에 중간 상태로 멈춘 건
SELECT id, status, created_at, updated_at
FROM request
WHERE status IN ('PENDING', 'PROCESSING')
  AND updated_at BETWEEN ? AND ?
ORDER BY created_at;
```

```sql
-- 유형 2: 외부는 실행되었는데 우리 기록이 확정되지 않은 건 (최우선 확인)
SELECT e.request_id, e.amount, e.status AS external_status, r.status AS local_status
FROM external_request e
JOIN request r ON r.id = e.request_id
WHERE e.status = 'EXECUTED'
  AND r.status <> 'COMPLETED'
  AND e.created_at BETWEEN ? AND ?;
```

점검 항목
* `[프로세스]` `INC-7-01` 장애 후 정합성 검증을 수행하는 것이 종료 조건에 포함되는가
* `[설계]` `INC-7-02` 중간 상태로 멈춘 건을 찾는 쿼리가 미리 준비되어 있는가
* `[프로세스]` `INC-7-03` 정정 내역이 감사 가능한 형태로 기록되는가

장애 중에 이 쿼리를 처음 작성하려 하면 시간이 오래 걸리고 실수가 나온다.
미리 만들어 런북에 붙여 둔다.

## 8. 런북

경보에는 대응 문서 링크가 붙어 있어야 한다.
받은 사람이 무엇을 해야 할지 모르는 경보는 소음이다.

런북 한 건의 구성 (등급 C)

```
## [경보 이름]

### 무엇을 뜻하는가
한 문장. 사용자에게 어떤 영향이 있는지 포함

### 즉시 확인할 것
1. 대시보드 링크 (바로 열리는 URL)
2. 확인할 지표와 정상 범위
3. 최근 배포 이력 링크

### 흔한 원인과 조치
| 원인 | 확인 방법 | 조치 |

### 완화 조치
되돌리기 쉬운 순서대로. 각 조치의 부작용 명시

### 에스컬레이션
언제, 누구에게

### 이 경보가 오발이었다면
임계치 조정 방법 또는 삭제 절차
```

점검 항목
* `[프로세스]` `INC-8-01` 모든 호출(page) 등급 경보에 런북이 있는가
* `[프로세스]` `INC-8-02` 런북이 실제 장애에서 도움이 되었는지 사후에 확인하는가
* `[프로세스]` `INC-8-03` 런북에 적힌 링크와 명령이 아직 유효한가

런북은 방치되면 빠르게 낡는다. 대시보드 주소가 바뀌고, 명령이 동작하지 않고, 담당자가 퇴사한다.
사용될 때마다 갱신 여부를 확인하는 것이 가장 현실적인 유지 방법이다.

## 9. 사후 분석

점검 항목
* `[프로세스]` `INC-9-01` SEV1과 SEV2에 대해 사후 분석을 반드시 수행하는가
* `[프로세스]` `INC-9-02` 개인의 책임이 아니라 시스템의 결함을 다루는가
* `[프로세스]` `INC-9-03` 후속 조치에 담당자와 기한이 있는가
* `[프로세스]` `INC-9-04` 후속 조치의 완료 여부를 추적하는가

Google SRE의 정의에 따르면 사후 분석 기록은 사건, 영향, 완화와 해결을 위해 취한 조치, 근본 원인, 재발 방지를 위한 후속 조치를 담는다.
출처: https://sre.google/sre-book/managing-incidents/

비난하지 않는 것이 규범인 이유는 관대함 때문이 아니라 정보 때문이다.
책임을 물으면 사람들이 정보를 감추고, 그러면 개선할 기회 자체가 사라진다.

```
## 사후 분석: [제목]

### 요약
무슨 일이 있었는지 세 문장 이내

### 영향
- 사용자 영향: 몇 명, 어떤 기능, 얼마 동안
- 에러 예산 소진: %
- 금전 영향: 있으면 금액

### 시간순 기록
| 시각 | 사건 | 근거(로그, 지표) |
탐지 시각, 선언 시각, 완화 시각, 종료 시각을 반드시 포함

### 근본 원인
왜 발생했는가. "누가 실수했다"가 아니라 "왜 그 실수가 가능했는가"

### 잘 된 것
탐지가 빨랐다면 왜 빨랐는지도 기록한다. 유지해야 할 것을 알기 위해

### 아쉬운 것
탐지가 늦었다면 왜 늦었는가. 완화가 늦었다면 무엇이 막았는가

### 운이 좋았던 것
우연히 피한 더 큰 피해. 다음에는 운이 없을 수 있다

### 후속 조치
| 내용 | 유형(탐지/완화/방지) | 담당 | 기한 | 상태 |
```

"운이 좋았던 것" 항목이 중요하다.
근무 시간이라 빨리 발견됐다거나, 트래픽이 적은 시간대였다는 이유로 피해가 작았다면 그것은 개선이 아니라 우연이다.

## 10. 훈련

절차는 연습하지 않으면 장애 때 작동하지 않는다.

점검 항목
* `[프로세스]` `INC-10-01` 복원 절차를 정기적으로 실제로 수행해 보는가
* `[프로세스]` `INC-10-02` 팀원이 역할을 돌아가며 맡아 보는가
* `[프로세스]` `INC-10-03` 훈련에서 발견된 문제를 문서에 반영하는가

훈련 유형 (주기는 등급 C)

| 유형 | 내용 | 주기 |
|------|------|------|
| 도상 훈련 | 가상 시나리오로 절차만 따라가 본다. 시스템은 건드리지 않는다 | 분기 1회 |
| 복원 리허설 | 격리 환경에 백업을 실제로 복원해 RTO를 측정한다 | 분기 1회 |
| 페일오버 훈련 | 계획된 시간에 실제로 복제본을 승격해 본다 | 반기 1회 |
| 장애 주입 | 운영 유사 환경에서 인스턴스나 의존성을 의도적으로 죽인다 | 반기 1회 |

도상 훈련은 비용이 거의 들지 않는데 효과가 크다.
"이 시점에 누가 무엇을 하는가"를 말로 따라가 보는 것만으로 절차의 빈 곳이 드러난다.

## 11. 측정 지표

| 지표 | 의미 | 목표 (등급 C) |
|------|------|---------------|
| MTTD | 발생부터 인지까지 | 5분 이하 |
| 선언까지 걸린 시간 | 인지부터 장애 선언까지 | 5분 이하 |
| MTTM | 인지부터 완화까지 | 30분 이하 |
| MTTR | 인지부터 완전 복구까지 | RTO 이내 |
| 사후 분석 수행률 | SEV1, SEV2 대비 | 100% |
| 후속 조치 완료율 | 기한 내 완료 비율 | 80% 이상 |
| 재발률 | 같은 원인의 반복 발생 | 추세 감소 |

완화까지의 시간(MTTM)을 별도로 보는 것이 중요하다.
완전 복구가 오래 걸려도 사용자 영향이 30분 안에 사라졌다면 대응은 성공한 것이다.

후속 조치 완료율이 낮다면 사후 분석은 형식이 된다.
장애를 겪고 문서를 쓰고 아무것도 바꾸지 않으면 같은 장애가 다시 온다.
