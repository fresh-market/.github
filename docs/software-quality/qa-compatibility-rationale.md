# 호환성 점검 항목의 근거

판정용 항목 목록은 [qa-compatibility-guideline.md](./qa-compatibility-guideline.md) 에 있다.
이 문서는 왜 그 기준인지와 예시를 담는다.

같은 환경을 공유하면서 다른 제품과 정보를 교환하고 기능을 수행할 수 있는 정도를 뜻한다.

하위 특성
* **공존성(co-existence)**: 자원을 공유하면서 서로에게 악영향을 주지 않는 정도
* **상호운용성(interoperability)**: 정보를 교환하고 활용할 수 있는 정도

백엔드에서는 실질적으로 **API 계약과 데이터 스키마의 하위 호환**이 이 속성의 전부다.
점검 항목의 대부분이 `[설계]`와 `[프로세스]` 층위에 있다. 코드 한 줄이 아니라 계약과 배포 순서가 판정 대상이기 때문이다.

> **수치에는 근거 등급이 표시되어 있다.**
> A는 산술로 도출된 값, B는 출처가 있는 값(링크 표기), C는 근거 없이 정한 예시값이다.
> C로 표시된 값은 그대로 채택하지 말고 측정 후 팀이 확정한다.
> 등급 정의는 quality-attributes.md의 "판정 기준 수치의 성격"을 참고한다.

## 1. 왜 하위 호환이 중요한가

API 소비자(웹, 모바일 앱, 파트너사, 내부 다른 서비스)는 우리 배포 주기와 무관하게 동작한다.
모바일 앱은 사용자가 업데이트하지 않으면 몇 달 전 버전이 계속 살아 있다.
따라서 서버가 계약을 깨는 순간 즉시 장애가 된다.

## 2. 호환을 깨는 변경

점검 항목
* `[설계]` `CMP-2-01` 이번 변경이 하위 호환을 깨는지 확인했는가
* `[설계]` `CMP-2-02` 깨는 변경이라면 새 메이저 버전으로 분리했는가
* `[설계]` `CMP-2-03` 안정성 단계(alpha, beta, stable)를 명확히 했는가
* `[프로세스]` `CMP-2-04` 폐기 예고부터 제거까지의 기간을 지켰는가

다음은 모두 호환을 깨는 변경이다.

| 변경 | 왜 깨지는가 |
|------|-------------|
| 필수 필드 추가 | 기존 클라이언트 요청이 검증에서 거부된다 |
| 필드 제거 또는 이름 변경 | 기존 클라이언트가 참조하던 값이 사라진다 |
| 타입 변경 | 파싱이 실패한다 (숫자 -> 문자열 등) |
| 기존 목록 메서드에 페이지네이션 추가 | 전체를 받던 클라이언트가 일부만 받는다 |
| 검증 규칙 강화 | 지금까지 통과하던 요청이 거부된다 |
| enum 값 추가 | 클라이언트가 미지의 값에 대비하지 않았다면 깨진다 |
| 기본값 변경 | 값을 생략하던 클라이언트의 동작이 바뀐다 |

판정 기준

안정성 단계 구분과 버전을 경로에 두는 방식, 호환을 깨는 변경의 목록은 Google AIP-180과 AIP-185에 근거한다 (등급 B).
출처: https://google.aip.dev/180 , https://google.aip.dev/185

반면 아래 표의 **폐기 예고 기간(30일, 180일)은 근거 없이 정한 값이다 (등급 C)**.
AIP는 하위 호환을 깨지 말라는 원칙과 버전 분리 방식을 규정하지만, 구체적인 유예 기간은 정하지 않는다.
클라이언트 업데이트 주기(특히 모바일 앱의 강제 업데이트 정책)를 확인한 뒤 팀이 정해야 한다.

| 안정성 단계 | 하위 호환 보장 | 폐기 예고 기간 (등급 C) | 표기 |
|-------------|----------------|----------------|------|
| alpha | 없음. 예고 없이 변경 가능 | 없음 | `/v1alpha1/` |
| beta | 최선 노력 | 30일 | `/v1beta1/` |
| stable | 보장 | 180일 | `/v1/` |

stable API에서 필드를 제거하려면 예고 후 180일, 그리고 해당 필드를 참조하는 트래픽이 사라진 것을 확인한 뒤에 한다.
기간만 채우고 트래픽 확인을 건너뛰면 남아 있는 구버전 클라이언트가 깨진다.

```java
// 점검 대상: 기존 필드를 이름만 바꿈 -> 구버전 클라이언트 전부 깨짐
public record RecordResponse(Long id, BigDecimal totalPrice) {}   // amount -> totalPrice

// 개선: 새 필드를 추가하고 기존 필드는 폐기 기간 동안 함께 내려준다
public record RecordResponse(
    Long id,
    @Deprecated BigDecimal amount,
    BigDecimal totalPrice
) {}
```

### 폐기 절차

```
필드 또는 엔드포인트 폐기 시 순서

1. D-180  새 필드 추가, 기존 필드와 동시 제공
          응답 헤더에 Deprecation, Sunset 명시
          문서에 폐기 예정과 대체 방법 기재
2. D-150  기존 필드 참조 트래픽을 메트릭으로 계측 시작
3. D-90   주요 클라이언트 팀에 개별 통지, 남은 사용처 확인
4. D-30   기존 필드 응답에 경고 로그, 사용 중인 클라이언트 식별
5. D-0    참조 트래픽이 0인 것을 7일 연속 확인한 뒤 제거
          확인되지 않으면 제거하지 않고 기간을 연장한다
```

날짜가 됐다는 이유만으로 제거하지 않는다. 판정 근거는 달력이 아니라 트래픽이다.

```
Deprecation: Wed, 30 Jul 2026 00:00:00 GMT
Sunset: Sat, 26 Jan 2027 00:00:00 GMT
Link: <https://docs.example.com/migration/record-amount>; rel="deprecation"
```

## 3. 확장에 안전한 계약 설계

점검 항목
* `[설계]` `CMP-3-01` 응답에 모르는 필드가 추가되어도 클라이언트가 깨지지 않는 전제를 문서화했는가
* `[설계]` `CMP-3-02` enum 대신 확장 가능한 문자열 코드를 쓸지 검토했는가
* `[코드]` `CMP-3-03` 알 수 없는 enum 값 수신 시 예외 대신 안전한 기본 처리를 하는가

목록 응답의 페이지네이션 구조는 backend 저장소의 `api-design-guideline.md`가 소유한다 (AIP-158 근거).

```java
// 점검 대상: 배열을 그대로 반환 -> 나중에 페이지 정보를 넣을 자리가 없다
public List<RecordResponse> list() { ... }

// 개선: 처음부터 감싸 두면 필드 추가로 확장할 수 있다
public record RecordListResponse(
    List<RecordResponse> records,
    String nextPageToken
) {}
```

목록에 페이지네이션을 나중에 추가하는 것은 호환을 깨는 변경이므로, 처음부터 넣는 편이 싸다.

판정 기준 (등급 C. 근거 없음)

| 항목 | 시작값 |
|------|--------|
| 기본 페이지 크기 | 20 |
| 최대 페이지 크기 | 100 |
| 페이지 토큰 유효 기간 | 1시간 |

## 4. 오류 응답의 상호운용성

오류는 사람이 읽는 문장이 아니라 기계가 판단할 수 있는 구조여야 한다.

점검 항목
* `[코드]` `CMP-4-01` 표준 상태 코드를 쓰는가
* `[코드]` `CMP-4-02` 기계 판독용 식별자(reason, domain)를 포함하는가
* `[설계]` `CMP-4-03` 어떤 오류가 재시도 가능한지 정의했는가
* `[코드]` `CMP-4-04` 오류 메시지가 내부 구현이나 민감 정보를 노출하지 않는가

```json
{
  "error": {
    "code": 404,
    "status": "NOT_FOUND",
    "message": "Record 456 was not found under user 123.",
    "details": [
      {
        "reason": "RECORD_NOT_FOUND",
        "domain": "api.example.com",
        "metadata": { "user": "123", "record": "456" }
      }
    ]
  }
}
```

클라이언트가 메시지 문자열을 파싱해서 분기하고 있다면, 메시지 문구를 다듬는 것만으로도 장애가 난다.
분기 근거는 항상 `reason` 같은 코드여야 한다.

`reason` 값은 계약의 일부다. 한 번 내보낸 값은 필드명과 동일한 수준으로 유지한다.
새 오류 상황이 생기면 기존 값의 의미를 바꾸지 말고 새 값을 추가한다.

## 5. 데이터 스키마 호환

API만 계약이 아니다. DB 스키마와 메시지 스키마도 계약이다.

> 이 절은 `qa-flexibility-rationale.md` 5장과 세 항목이 겹친다.
> 컬럼 제거 단계는 `fresh-market/fm-infra`의 `INF-6-01`이 이 인프라의 확정 규칙으로 더 구체적이므로,
> 겹칠 때는 그쪽만 발화하고 여기는 억제된다.

점검 항목
* `[프로세스]` `CMP-5-01` 배포와 스키마 변경이 서로를 강제하지 않는가 (한쪽만 롤백 가능한가)
* `[설계]` `CMP-5-02` 컬럼 제거를 단계로 나눴는가
* `[설계]` `CMP-5-03` 메시지 큐 이벤트에 버전이나 확장 여지가 있는가
* `[인프라]` `CMP-5-04` DDL이 온라인으로 수행 가능한지 확인했는가

배포 순서가 어긋나도 깨지지 않아야 한다.
구버전 코드와 신버전 스키마가 잠시 공존하는 구간이 반드시 생기기 때문이다.

```sql
-- 점검 대상: NOT NULL 컬럼을 기본값 없이 추가 -> 구버전 코드의 INSERT가 실패
ALTER TABLE record ADD COLUMN channel VARCHAR(20) NOT NULL;

-- 개선: nullable로 추가한 뒤, 코드 배포와 데이터 이관 후 제약을 조인다
ALTER TABLE record ADD COLUMN channel VARCHAR(20) NULL,
    ALGORITHM=INPLACE, LOCK=NONE;
```

`ALGORITHM=INPLACE, LOCK=NONE`을 명시하면 온라인 수행이 불가능한 변경일 때 MySQL이 실행 대신 오류를 낸다.
모르고 테이블 전체를 잠그는 사고를 막을 수 있다.

판정 기준 (등급 C. 근거 없음)

| 항목 | 기준 |
|------|------|
| 온라인 DDL 필수 대상 | 행 수 100만 이상 테이블 |
| 배포 롤백 가능 기간 | 스키마 변경 후 최소 1회 배포 주기 |
| 컬럼 제거 최소 단계 | 4단계 (추가 -> 양쪽 쓰기 -> 읽기 전환 -> 제거) |

## 6. 공존성

같은 자원(DB, 캐시, 큐)을 여러 애플리케이션이 공유할 때의 문제다.

점검 항목
* `[인프라]` `CMP-6-01` 배치와 API 서버가 같은 DB 커넥션 자원을 잠식하지 않는가
* `[프로세스]` `CMP-6-02` 대량 배치가 운영 시간대 쿼리 성능에 영향을 주지 않는가
* `[설계]` `CMP-6-03` 캐시 키 네임스페이스가 서비스별로 분리되어 있는가

배치가 대량 조회로 커넥션풀을 다 쓰면 API가 커넥션을 못 받아 함께 죽는다.

판정 기준 (등급 C. 근거 없음)

| 항목 | 기준 |
|------|------|
| 배치 전용 커넥션 비율 | DB 최대 커넥션의 20% 이하 |
| 배치 실행 시간대 | 트래픽 하위 20% 구간 |
| 배치 청크 크기 | 1000행. 청크 사이에 짧은 대기 |
| 배치의 읽기 대상 | 가능하면 복제본(replica) |

```yaml
# 개선: 배치와 API가 서로 다른 데이터소스와 풀을 쓰도록 분리한다
spring:
  datasource:
    api:
      hikari:
        pool-name: api-pool
        maximum-pool-size: 30
        connection-timeout: 3000
    batch:
      hikari:
        pool-name: batch-pool
        maximum-pool-size: 5        # 배치가 잠식할 수 있는 상한을 좁게
        connection-timeout: 10000   # 배치는 대기를 더 견딜 수 있다
```

캐시 키는 서비스와 버전을 접두어로 둔다.

```
<앱이름>:v1:resource:12345              # 서비스, 스키마 버전, 도메인, 식별자
<앱이름>:v1:resource:available:12345
```

버전 접두어가 있으면 캐시 구조 변경 시 기존 키를 삭제하지 않고 접두어만 올려 자연 만료시킬 수 있다.

## 7. 상호작용 능력 관점

ISO 25010:2023의 상호작용 능력(interaction capability)은 최종 사용자 UI를 전제하지만, API 서버에서는 API 소비자의 사용성으로 나타난다.

점검 항목
* `[설계]` `CMP-7-01` 리소스와 필드 명명이 API 전체에서 일관되는가
* `[프로세스]` `CMP-7-02` 모든 메서드, 리소스, 필드에 문서가 있는가
* `[코드]` `CMP-7-03` 오류 메시지가 해결 방향을 제시하는가

판정 기준 (등급 C. 근거 없음)

| 항목 | 기준 |
|------|------|
| 명명 규칙 | 필드는 snake_case 또는 camelCase 중 하나로 통일. 혼용 금지 |
| 시각 필드 | 접미어 `_at`, 값은 RFC 3339 UTC |
| 기간 필드 | 접미어에 단위 명시 (`timeout_seconds`) |
| 문서 누락 | 공개 필드 중 설명 없는 것 0개 |

이름이 일관되지 않으면 클라이언트 개발자가 매번 문서를 다시 찾아봐야 한다.
자기서술성(self-descriptiveness)은 문서 없이도 응답만 보고 의미를 알 수 있는 정도를 말한다.

## 8. 측정 지표

| 지표 | 의미 | 목표 (예시값) |
|------|------|---------------|
| 호환 파괴 변경 발생 건수 | 계약 안정성 | stable API에서 0건 |
| 구버전 API 트래픽 비율 | 폐기 가능 시점 판단 | 제거 전 0% 확인 |
| 폐기 예고부터 제거까지 기간 | 클라이언트 대응 여유 | stable 180일 이상 |
| 스키마 변경 롤백 성공률 | 배포 안전성 | 100% |
| 문서 누락 필드 수 | 자기서술성 | 0개 |
