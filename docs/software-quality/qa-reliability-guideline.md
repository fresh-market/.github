# 신뢰성 점검 항목

명시된 조건에서 명시된 기간 동안 의도한 기능을 수행하는 정도를 뜻한다.

**이 문서는 판정용이다.** 항목과 판정 기준만 담고, 왜 그 기준인지와 예시 코드는
[qa-reliability-rationale.md](./qa-reliability-rationale.md) 에 있다.

코드 한 줄로 판단하기 어렵고 시스템 구성 단위에서 결정되는 영역이라
`[인프라]` 와 `[프로세스]` 비중이 높다.

## 1. 가용성 목표

점검 항목
* `[설계]` `REL-1-01` 기능 등급별로 가용성 목표를 다르게 정했는가
  전체에 하나의 목표를 걸면 부가 기능 때문에 핵심 거래의 예산이 깎인다.
* `[설계]` `REL-1-02` 목표가 백분위수와 기간을 포함한 문장으로 적혀 있는가
  "30일 이동 기간 기준으로 성공 응답 비율 99.95% 이상, p99 300ms 이하" 형태여야 한다.
* `[프로세스]` `REL-1-03` 목표 대비 실적을 정기적으로 확인하는 자리가 있는가

가용성과 허용 다운타임 (등급 A. 산술 도출)

| 가용성 | 연간 | 월간 |
|--------|------|------|
| 99% | 약 3.65일 | 약 7.3시간 |
| 99.9% | 약 8.76시간 | 약 43.8분 |
| 99.95% | 약 4.38시간 | 약 21.9분 |
| 99.99% | 약 52.6분 | 약 4.4분 |

기능 등급별 목표 (등급 C. 근거 없음)

| 기능 등급 | 판단 기준 | 목표 |
|-----------|-----------|------|
| 핵심 거래 | 실패 시 금전 손실이나 데이터 유실 | 99.95% |
| 주요 조회 | 실패 시 주 사용 흐름이 막힘 | 99.9% |
| 부가 기능 | 없어도 주 흐름은 동작 | 99.5% |
| 내부 도구 | 사용자 대면이 아님 | 99% |

## 2. 외부 연동 타임아웃

점검 항목
* `[코드]` `REL-2-01` 모든 외부 호출에 연결 타임아웃과 읽기 타임아웃이 설정되어 있는가
  가장 위험한 것은 외부가 죽는 경우가 아니라 느려지는 경우다. 우리 스레드가 묶인다.
* `[인프라]` `REL-2-02` 타임아웃 값이 상위 호출자의 타임아웃보다 짧은가 (타임아웃 예산 배분)
  반대가 되면 상위가 먼저 끊겨 하위 작업이 고아가 된다.
* `[인프라]` `REL-2-03` DB 커넥션 획득과 쿼리 실행에도 타임아웃이 있는가
  `max-lifetime` 은 DB 의 `wait_timeout` 보다 짧아야 간헐적 연결 오류가 없다.

판정 기준 (등급 C. 근거 없음)

| 구간 | 연결 | 읽기 | 근거 |
|------|------|------|------|
| API 게이트웨이 | - | 10s | 사용자 인내 한계 |
| 서비스 간 호출 | 1s | 5s | 게이트웨이 예산의 절반 |
| 외부 연동 (결제, 알림, 인증) | 1s | 3s | 상위 예산 안에서 재시도 여유 확보 |
| DB 커넥션 획득 | 3s | - | 풀 고갈을 빠르게 드러냄 |
| DB 쿼리 | - | 5s | 장기 쿼리의 커넥션 점유 방지 |

관련 기본값 (등급 B)

| 항목 | 기본값 |
|------|--------|
| MySQL `wait_timeout`, `interactive_timeout` | 28800초 (8시간) |
| MySQL `max_execution_time` | 0 (비활성) |
| HikariCP `connectionTimeout` | 30000ms |
| HikariCP `maxLifetime` | 1800000ms (30분) |

## 3. 재시도와 멱등성

점검 항목
* `[코드]` `REL-2-04` 재시도 대상 연산이 멱등한가
  타임아웃 났다고 상태 변경 요청을 그냥 재시도하면 같은 작업이 두 번 실행된다.
* `[설계]` `REL-2-05` 재시도 가능한 오류와 불가능한 오류를 구분했는가
* `[코드]` `REL-2-06` 재시도 간격에 지수 백오프와 지터를 적용했는가
  지수 백오프만으로는 재시도가 특정 시점에 몰린다. 무작위성을 더해야 분산된다.
* `[코드]` `REL-2-07` 재시도 횟수에 상한이 있는가
* `[인프라]` `REL-2-08` 재시도 총 소요 시간이 상위 타임아웃 예산 안에 들어오는가

판정 기준 (지터 방식은 등급 B, 나머지는 등급 C)

| 항목 | 값 | 등급 |
|------|-----|------|
| 지터 적용 | 필수 | B |
| 지터 방식 | 일반 재시도는 Full Jitter, 스로틀링 응답은 Equal Jitter | B |
| 최대 재시도 횟수 | 3회 | C |
| 초기 대기 | 200ms | C |
| 배수 | 2배 | C |

재시도 가능 여부

| 상황 | 재시도 | 이유 |
|------|--------|------|
| 연결 실패, 타임아웃, 503 | 가능 | 일시적 가용성 문제 |
| 429 | 가능. `Retry-After` 준수 | 서버가 대기 시간을 지정 |
| 500 | 조건부 | 멱등한 연산만 |
| 400, 422 | 불가 | 같은 요청은 계속 실패한다 |
| 401, 403 | 불가 | 자격 갱신 없이는 동일 결과 |

## 4. 서킷 브레이커와 격벽

점검 항목
* `[인프라]` `REL-2-09` 실패율이 임계치를 넘으면 호출을 끊고 빠르게 실패하는가
* `[인프라]` `REL-2-10` 외부 연동별로 스레드풀 또는 커넥션풀이 분리되어 있는가
  격벽이 없으면 부가 기능 한 곳의 지연이 전체 스레드풀을 잠식해 핵심 거래까지 멈춘다.
* `[설계]` `REL-2-11` 차단 상태에서의 대체 동작(fallback)이 정의되어 있는가
* `[설계]` `REL-2-12` 대체 동작이 안전한지 검토했는가
  한정 자원의 잔여 수량과 금전 처리는 대체값을 쓰지 않고 실패 처리한다.

판정 기준 (등급 B. Resilience4j 2.2.0 기본값 기준)

| 설정 | 기본값 | 제안 | 사유 |
|------|--------|------|------|
| `failureRateThreshold` | 50% | 50% | 기본값 사용 |
| `minimumNumberOfCalls` | 100건 | 20건 | 호출량이 적으면 100건 전에 장애가 지나간다 |
| `waitDurationInOpenState` | 60초 | 30초 | 회복 확인 주기를 앞당김 |
| `permittedNumberOfCallsInHalfOpenState` | 10건 | 5건 | 회복 확인 비용 절감 |
| `slowCallRateThreshold` | 100% | 50% | 완전 실패 전에 느린 호출로 차단 |
| `slowCallDurationThreshold` | 60초 | 읽기 타임아웃의 60% | 타임아웃 이전에 감지 |

기본값에서 벗어난 값은 위 사유가 그 서비스에 해당할 때만 쓴다.

대체 동작

| 기능 유형 | 대체 동작 |
|-----------|-----------|
| 부가 정보 목록 | 빈 배열 |
| 예측값, 추정 정보 | 안내 문구로 대체 |
| 한정 자원의 잔여 수량 | 대체값 금지. 실패 처리 |
| 금전 처리 | 대체값 금지. 실패 처리 |

## 5. 결함 허용과 부하 차단

점검 항목
* `[인프라]` `REL-3-01` 과부하 시 전체가 느려지는 대신 일부를 거절하는가 (load shedding)
  모두를 조금씩 느리게 하면 전원 실패로 끝나고, 일부를 거절하면 대부분이 성공한다.
* `[인프라]` `REL-3-02` 큐 길이와 대기 시간에 상한이 있는가
* `[설계]` `REL-3-03` 우선순위가 낮은 기능을 먼저 끌 수 있는가 (graceful degradation)
* `[프로세스]` `REL-3-04` 기능을 끄는 스위치를 배포 없이 조작할 수 있는가
  장애 한복판에서 배포를 해야만 끌 수 있다면 그 스위치는 없는 것과 같다.

판정 기준 (등급 C. 근거 없음)

| 항목 | 시작값 | 근거 |
|------|--------|------|
| 요청 대기 큐 길이 | 스레드풀 크기의 2배 | 그 이상은 처리 전에 클라이언트가 포기한다 |
| 큐 대기 시간 상한 | 1초 | 대기가 길면 이미 무의미한 요청이다 |
| 거절 시작 지점 | CPU 사용률 80% 지속 | 포화 직전에 차단 |

## 6. 복구성

실제 장애 시 사람이 수행하는 절차는 [qa-incident-response-guideline.md](./qa-incident-response-guideline.md) 에 있다.

점검 항목
* `[설계]` `REL-4-01` 트랜잭션 경계가 복구 단위와 일치하는가
* `[코드]` `REL-4-02` checked 예외에서 롤백이 동작하는가
  Spring `@Transactional` 은 기본적으로 unchecked 예외에만 롤백한다. `rollbackFor` 를 지정하거나 도메인 예외로 변환한다.
* `[프로세스]` `REL-4-03` 백업뿐 아니라 복원을 실제로 리허설했는가
  복원해 본 적 없는 백업은 백업이 아니다. 분기 1회 이상 수행하고 기록한다.
* `[설계]` `REL-4-04` RPO와 RTO를 숫자로 정의했는가
* `[인프라]` `REL-4-05` 백업이 원본과 다른 장애 도메인에 저장되는가

판정 기준 (등급 C. 근거 없음)

| 데이터 등급 | 판단 기준 | RPO | RTO |
|-------------|-----------|-----|-----|
| 금전, 자원 이동 기록 | 유실 시 금전 손실이나 법적 문제 | 0 | 1시간 |
| 사용자 생성 거래 데이터 | 유실 시 다시 만들 수 없음 | 5분 | 4시간 |
| 운영 기준 데이터 | 재입력 가능하나 비용이 큼 | 1시간 | 8시간 |
| 파생 데이터 | 원본에서 재생성 가능 | 재생성 가능 | 24시간 |

등급을 나누지 않고 전부 RPO 0으로 잡으면 감당할 수 없는 비용이 된다.

## 7. 배포와 헬스체크

점검 항목
* `[인프라]` `REL-5-01` 헬스체크가 의존 컴포넌트 상태를 반영하는가
* `[인프라]` `REL-5-02` 기동 완료 전에 트래픽을 받지 않는가 (readiness와 liveness 분리)
* `[인프라]` `REL-5-03` 종료 시 처리 중인 요청을 마치고 내려가는가 (graceful shutdown)
* `[인프라]` `REL-5-04` liveness가 외부 의존성 상태에 좌우되지 않는가
  liveness 가 DB 까지 보면 DB 순단에 애플리케이션이 통째로 재시작되며 상황이 악화된다.

판정 기준 (등급 C. 근거 없음)

| 항목 | 시작값 | 근거 |
|------|--------|------|
| graceful shutdown 대기 | 30초 | 대부분의 요청이 끝나는 시간 |
| readiness 실패 임계 | 연속 3회 | 순간 지연으로 트래픽이 끊기는 것 방지 |
| liveness 실패 임계 | 연속 5회 | 재시작은 최후 수단 |
