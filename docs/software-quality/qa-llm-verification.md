# LLM 기반 품질 검증 설계

이 문서군의 점검 항목을 LLM으로 자동 판정하려 할 때의 설계 방안과 그 한계를 다룬다.

다른 문서가 "무엇을 점검하는가"를 정한다면, 이 문서는 "그 점검을 누가 어떻게 수행하는가"를 정한다.
품질 속성 문서가 아니므로 ISO/IEC 25010과의 매핑은 없다.

> **수치에는 근거 등급이 표시되어 있다.**
> A는 산술로 도출된 값, B는 출처가 있는 값(링크 표기), C는 근거 없이 정한 예시값이다.
> C로 표시된 값은 그대로 채택하지 말고 측정 후 팀이 확정한다.
> 등급 정의는 quality-attributes.md의 "판정 기준 수치의 성격"을 참고한다.

## 1. 판정 가능성을 지배하는 세 가지 제약

설계에 앞서 이 문서군의 실제 구성을 집계했다.
아래 세 절의 수치는 문서를 세어 얻은 값이므로 등급 A다. 재현 방법은 9장에 있다.

### 1.1 점검 항목의 71%가 코드 밖에 있다

`qa-*.md` 11개 문서의 불릿 점검 항목은 217건이며, 층위별 분포는 다음과 같다 (등급 A).

| 층위 | 건수 | 비중 |
|------|------|------|
| `[코드]` | 77 | 35.5% |
| `[설계]` | 44 | 20.3% |
| `[인프라]` | 46 | 21.2% |
| `[프로세스]` | 50 | 23.0% |

quality-attributes.md가 명시하듯 PR 단위로 판정할 수 있는 것은 `[코드]` 항목뿐이다.
따라서 **PR diff만 입력으로 주는 LLM 검증은 29%가 상한이다.**
나머지 71%를 판정하려면 LLM을 개선하는 것이 아니라 입력을 바꿔야 한다.

### 1.2 점검 항목의 86%가 부재를 묻는다

점검 항목을 문장 형태로 나누면 다음과 같다 (등급 A).

| 형태 | 예 | 건수 | 비중 |
|------|-----|------|------|
| 부정형 (있는 것을 지적) | "쿼리를 문자열 연결로 조립하지 않는가" | 29 | 13.4% |
| 긍정형 (없는 것을 지적) | "모든 외부 호출에 타임아웃이 설정되어 있는가" | 188 | 86.6% |

층위별로 보면 더 뚜렷하다.

| 층위 | 부정형 | 긍정형 |
|------|--------|--------|
| `[코드]` | 20 | 42 |
| `[설계]` | 2 | 61 |
| `[인프라]` | 3 | 39 |
| `[프로세스]` | 4 | 46 |

이 분포가 설계의 핵심 과제를 결정한다.
LLM은 diff에 **있는** 코드를 평가하는 데는 강하지만, diff에 **없는** 것을 알아채는 데는 현저히 약하다.
"타임아웃이 없다", "예외 경로가 비어 있다", "인덱스가 없다"는 모두 보이지 않는 것을 보는 판정이다.

부재 판정을 그대로 두면 재현율이 낮고, 낮은 재현율은 "통과했으니 괜찮다"는 잘못된 신호를 준다.
이것이 오탐보다 위험하다. 3장과 4장은 이 문제에 대한 대응이다.

### 1.3 판정 기준 수치의 대부분이 등급 C다

이 문서군의 임계치 대부분은 근거 없이 정한 예시값이다.
따라서 **LLM에게 값의 옳고 그름을 판정시켜서는 안 된다.**

| 질문 | 판정 | 이유 |
|------|------|------|
| "커넥션풀 30은 적절한가" | 불가 | 등급 C 값이다. LLM에게 정답이 없다 |
| "커넥션풀 값이 명시되어 있는가" | 가능 | 설정 파일에 증거가 있다 |
| "그 값의 산정 근거가 기록되어 있는가" | 가능 | ADR 존재 여부로 판정한다 |

구조 판정과 값 판정을 섞으면, LLM이 근거 없는 숫자를 근거 있는 것처럼 단정하게 된다.
등급 C 수치에 대해 LLM이 낼 수 있는 판정은 "정해졌고 기록되었는가"까지다.

## 2. 4단 게이트

층위마다 증거가 나타나는 시점과 형태가 다르다.
한 게이트에 전부 밀어 넣으면 `[프로세스]` 항목까지 PR 리뷰 지적처럼 보여 소음이 된다.
문서군이 층위 표기를 도입한 것과 같은 이유로 게이트도 나눈다.

| 게이트 | 시점 | 입력(증거) | 담당 층위 | 차단 |
|--------|------|-----------|-----------|------|
| G-BUILD | PR 생성 시와 이후 매 push | 빌드 산출물 | 커버리지, 정적 분석 | **차단** |
| G-LOCAL | 커밋 직후. 개발자가 직접 실행 | 마지막 커밋의 변경분 + 앵커 파일 | 빌드 게이트 + 전체 567건 | 비차단 |
| G-PR | PR 생성 시와 이후 매 push (2.4절) | diff + 변경 파일 전체 + 앵커 파일(3장) | 활성화된 항목 전부. 2단계 실행 (2.0절) | 비차단 |
| G-DESIGN | 스키마, 계약, 의존성 변경 감지 시. G-PR과 같은 시점 | 마이그레이션 SQL, API 계약 diff, ADR | `[설계]` | 비차단. ADR 요구 |
| G-RELEASE | 배포 직전 | 부하 테스트 결과, 호환성 리포트, 롤백 가능성 | `[설계]`, `[프로세스]` 일부 | 차단 |
| G-AUDIT | 주기별. 1시간부터 6개월까지 (2.5절) | 운영 메트릭, 슬로우 쿼리 로그, 알림 이력, 기록물 | `[프로세스]` | 비차단. 티켓 생성 |

G-DESIGN은 G-PR과 시점이 같다. 별도 게이트로 둔 것은 담당 층위와 차단 여부가 다르기 때문이며, 실행 시점이 다른 것이 아니다.
G-RELEASE를 릴리스 태그 시점이 아니라 배포 직전에 두는 이유는, 태그를 찍은 뒤 차단하면 되돌리는 비용이 크고 성능 효율성 문서가 요구하는 것이 "주요 릴리스 **전**의 부하 테스트"이기 때문이다.

**LLM 판정 게이트는 차단하지 않는다.** G-LOCAL과 G-PR 모두 지적만 남기고 병합을 막지 않는다.

차단하는 것은 **도구가 판정하는 두 게이트뿐**이다.

| 게이트 | 판정 주체 | 차단 근거 |
|--------|-----------|-----------|
| G-BUILD | Gradle, SonarQube | 결정론적이다. 같은 코드에 같은 결과가 나온다 |
| G-RELEASE | 배포와 시험 스크립트 | AWS API 조회 결과가 이진이다 |

**차단 여부를 가르는 것은 게이트의 중요도가 아니라 판정의 재현성이다.**
JaCoCo가 커버리지 99%를 100%가 아니라고 판정하는 데는 오탐이 없다.
반면 LLM이 "타임아웃이 없다"고 판정하는 것은 재현율이 미측정이라 오탐 가능성이 남는다.

근거는 7.3절의 규율이다. **재현율이 측정되기 전에는 차단하지 않는다.**
지금 차단하면 근거 없는 등급 C 값으로 병합을 막는 셈이고, 오탐이 몇 번 쌓이면 곧 우회 문화가 생긴다.
우회가 관행이 되는 순간 나머지 게이트의 신뢰도까지 떨어진다.

차단으로 전환하는 조건은 6장에 있다. 항목별 정확도를 3개월 측정해 90%를 넘긴 항목에 한해 그것만 차단 후보로 올린다.

점검 항목
* `[프로세스]` `LLM-2-01` LLM 판정 게이트가 병합을 막지 않는가
* `[프로세스]` `LLM-2-02` 지적이 코멘트나 티켓으로 남아 추적되는가
* `[인프라]` `LLM-2-03` 게이트별로 활성화되는 점검 항목 목록이 분리되어 있는가

### 2.0 G-BUILD: 도구가 판정하는 차단 게이트

LLM 게이트보다 먼저 도는 결정론적 게이트다. 7.1절의 G1 등급 항목이 여기 속한다.

| 조건 | 기준 | 판정 주체 | 근거 |
|------|------|-----------|------|
| 커버리지 | `*.domain.service.*` 메서드 **100%** | Gradle `jacocoTestCoverageVerification` | 기술 스택 확정 문서 3.10절 |
| 정적 분석 | **신규 Blocker 이슈 0건** | SonarQube Quality Gate | 같은 문서 3.11절 |

**둘 중 하나라도 실패하면 병합을 차단한다.** 브랜치 보호의 필수 상태 검사가 강제 수단이다.

점검 항목과 Gradle 설정은 `fresh-market/fm-backend`의 `docs/code-architecture/build-gate-guideline.md`에 있다 (`BLD-*`).

**두 게이트의 판정 주체를 분리한 것이 중요하다.**
SonarQube Quality Gate에서 커버리지 조건을 제거하고 Gradle이 판정한다.
둘 다 커버리지를 판정하면 SonarQube 기본값(신규 코드 80% 등)이 Gradle 기준과 충돌한다.

**차단 조건을 `Blocker` 하나로 정한 이유가 있다.**
`Blocker`는 프로덕션에서 애플리케이션을 망가뜨릴 높은 확률의 버그를 뜻한다. 병합을 막을 근거가 되는 것은 이 등급뿐이다.
차단 대상을 넓히면 병합이 자주 막히고, 곧 강제 병합이 관행이 되어 게이트 자체가 무의미해진다.

#### 실행 순서

```
G-BUILD 실패  ->  여기서 멈춘다. LLM 게이트를 돌리지 않는다
G-BUILD 통과  ->  G-PR (LLM 판정) 진행
```

빌드가 깨진 코드에 판정 코멘트를 붙여도 읽히지 않는다. 무료 티어 요청도 낭비된다.

#### 로컬에서도 같은 게이트를 돌린다

**G-LOCAL은 LLM 판정에 앞서 빌드 게이트를 먼저 실행하고 결과를 알린다.**

```bash
./gradlew check    # jacocoTestCoverageVerification 포함
```

기준이 100%라 여유가 없다. **새 메서드를 하나 추가하고 테스트를 빠뜨리면 그 순간부터 모든 병합이 막힌다.**
CI에서 처음 알면 이미 PR을 연 뒤라 왕복이 생기므로 커밋 직후 로컬에서 확인한다.

로컬에서는 **차단하지 않고 결과만 알린다.** 작업 중 반복 실행하는 도구이므로 중간 상태에서 실패하는 것이 정상이다.

| | G-BUILD (CI) | G-LOCAL 의 빌드 단계 |
|---|---|---|
| 실행 | 자동 | 개발자 재량 |
| 커버리지 미달 시 | **병합 차단** | 알림만 |
| 정적 분석 Blocker 시 | **병합 차단** | 알림만 |

### 2.0.0 G-LOCAL 과 G-PR 의 역할 분담

두 게이트가 **서로 다른 모델로 서로 다른 항목을 판정한다.** 같은 항목을 둘 다 보면 뒤쪽이 중복이 된다.

| | G-LOCAL | G-PR |
|---|---|---|
| 모델 | Claude (개발자 로컬) | `gemini-2.5-flash` (Actions, 무료) |
| 실행 | 커밋 직후. 개발자 재량 | 자동 |
| 판정 범위 | **마지막 커밋의 변경분** | **PR 전체 누적 diff** |
| 판정 항목 | 활성화된 항목 전부 | 활성화된 항목 전부. **2단계로 나눠 실행** |
| 차단 | 안 함 | 안 함 |

**두 게이트의 차이는 항목이 아니라 범위와 속도다.**
G-LOCAL은 작업 중 반복 실행하는 도구라 마지막 커밋만 보고 빠르게 답한다.
G-PR은 병합 판단에 쓰이므로 **PR이 병합되면 무엇이 들어가는지**를 매번 전부 다시 본다.

증분만으로는 병합 판단을 할 수 없다.
커밋 1에서 지적된 위반을 고치지 않고 커밋 2, 3을 쌓으면, 증분 판정은 그 위반을 다시 보지 못한다.
누적 diff는 커밋 1의 변경을 계속 포함하므로 고칠 때까지 반복해서 지적된다.
2.2절의 기준선 비교(기존 부채와 신규 위반 구분)도 누적이 있어야 성립한다.

### 2.0.1 G-PR 의 2단계 실행

활성화 항목을 한 번에 다 물으면 뒤쪽 판정 품질이 떨어질 수 있다.
`gemini-2.5-flash`가 464건을 온전히 처리하는지 측정된 바 없으므로, **먼저 확실한 것을 끝내고 여유가 있으면 나머지를 한다.**

| 단계 | 항목 | 건수 | 수행 |
|------|------|------|------|
| 1단계 | `fresh-market/fm-backend` 코드 관용과 패턴 | 250 | **항상** |
| 2단계 | `fresh-market/.github` 품질 속성 + `fresh-market/fm-infra` 인프라 제약 | 204 | **조건부** |

`items.yml`의 `ci_stage` 필드가 이 구분을 담는다.

```yaml
- {id: EC-2-01, gates: [local, ci], ci_stage: 1, ...}   # backend
- {id: REL-2-01, gates: [local, ci], ci_stage: 2, ...}  # common
```

**2단계 진입 조건**

1단계 응답이 온전해야 한다. 하나라도 어긋나면 2단계를 건너뛴다.

| 확인 | 어긋났을 때의 의미 |
|------|--------------------|
| `finishReason`이 정상 종료인가 | 출력 상한에 걸려 잘렸다 |
| 응답 항목 수가 요청 항목 수와 같은가 | 일부를 판정하지 않았다 |
| 출력이 4장 구조로 파싱되는가 | 형식이 무너졌다 |
| 누적 토큰 사용량이 여유 안에 있는가 | TPM 한도에 근접했다 |

**2단계를 건너뛰어도 1단계 결과는 그대로 보고된다.** 폴백이 별도 장치 없이 성립한다.

호출이 2회가 되지만 RPM 10 안에 여유가 있고, 입력을 두 번 보내는 비용은 토큰이 무료라 문제가 되지 않는다 (10.5절).

**판정하지 않은 항목을 통과로 뭉뚱그리지 않는다.**
2단계를 건너뛰었거나 응답에서 빠진 항목은 `UNJUDGED`로 기록한다.
4장이 `INSUFFICIENT_EVIDENCE`를 `OK`와 구분한 것과 같은 이유다.

**2단계가 계속 실패하면 그것이 곧 답이다.** `gemini-2.5-flash`로는 204건을 감당하지 못한다는 뜻이므로, 그때 1단계만 남기거나 2단계를 더 잘게 나눈다.

`gates` 필드가 이 분담을 기계 판독 가능하게 담는다.

```yaml
- {id: EC-2-01, gates: [local, ci], ...}   # backend. 두 게이트가 모두 본다
- {id: REL-2-01, gates: [local], ...}      # common. G-LOCAL 만 본다
```

#### 이 배분이 닫은 것과 남긴 것

G-PR이 활성화 항목 전부를 누적으로 판정하므로, **모든 항목이 병합 전에 한 번은 누적 상태로 확인된다.**

| 항목군 | 증분 판정 | 누적 판정 |
|--------|-----------|-----------|
| backend 250건 | G-LOCAL | G-PR 1단계 |
| common 217건 + infra 90건 | G-LOCAL | G-PR 2단계 |

G-LOCAL을 건너뛰어도 G-PR이 전부 본다. **개발자 규율에 의존하지 않는다.**

**남는 위험은 하나다.** 2단계가 계속 실패하면 204건이 누적 판정을 받지 못한다.
그 경우 `UNJUDGED`가 쌓이므로 조용히 통과하지는 않고, 8장의 지표로 드러난다.

이때 취할 조치는 셋이다.

| 조치 | 내용 |
|------|------|
| 2단계를 더 잘게 나눈다 | 3단계, 4단계로. 호출이 늘어도 RPM 10 안에 여유가 있다 |
| 2단계 항목을 좁힌다 | 앵커 규칙의 `chapters`로 활성화 범위를 줄인다 |
| G-LOCAL 범위를 누적으로 바꾼다 | 도구가 무거워져 덜 돌리게 되는 대가가 있다. 마지막 수단 |

**앞의 둘을 먼저 시도한다.** 세 번째는 자동 게이트의 실패를 사람 규율로 메우는 것이라 구조적으로 약하다.

### 2.1 판정 기준은 두 층으로 나뉘어 있다

판정에 필요한 문서가 한 곳에 있지 않다.

| 층 | 내용 | 위치 |
|----|------|------|
| 점검 항목 | 무엇을 점검하는가. 수치는 대부분 등급 C 예시값 | `fresh-market/.github` 의 `docs/software-quality/` |
| 확정값 | 이 팀이 실제로 정한 목표치와 보장 메커니즘 | `fresh-market/fm-infra` 의 `docs/system-design/` |

quality-attributes.md의 "도메인에 맞게 채워야 하는 부분"이 두 층의 관계를 규정한다.
앞 층이 빈칸을 만들고 뒤 층이 채운다.
예를 들어 신뢰성 문서는 RPO와 RTO 표를 등급 C로 제시하고, 확정값 문서가 시나리오별 실제 목표와 보장 메커니즘을 정한다.

**확정값 문서는 항상 필요한 것이 아니다.**
1.3절이 나눈 판정 유형에 따라 갈린다.

| 판정 유형 | 예 | 확정값 문서 |
|-----------|-----|-------------|
| 구조 판정 | "타임아웃이 설정되어 있는가" | 불필요 |
| 값 판정 | "타임아웃 3초가 적절한가" | 애초에 하지 않는다 (1.3절) |
| 근거 판정 | "그 값의 산정 근거가 기록되어 있는가" | 필요 |
| 일치 판정 | "설정값이 확정값과 같은가" | 필요 |

`[코드]` 항목은 대부분 구조 판정이다.
"쿼리를 문자열 연결로 조립하지 않는가", "예외를 삼키지 않는가", "소유권을 검증하는가"는 코드만 보면 판정되며 확정값 유무와 결과가 같다.

확정값이 필요한 것은 근거 판정과 일치 판정이고, 주로 `[설계]`와 `[인프라]` 항목이다.
7.1절에서 G3와 G4로 분류한 `[설계]` 30건이 대체로 여기 해당한다.

확정값이 없다고 해서 등급 C 예시값으로 판정하는 것이 아니다.
그 경우 값 판정을 하지 않을 뿐이며, 그것이 1.3절이 요구한 동작이다.

### 2.1.1 의존은 부분적이다

따라서 기준 저장소 체크아웃은 조건부로 건다.
활성화된 항목 집합에 근거 판정이나 일치 판정이 포함될 때만 확정값 문서를 가져온다.

```yaml
- uses: actions/checkout@v4
  if: needs.scope.outputs.needs-baseline-values == 'true'
  with: { repository: fresh-market/fm-infra, path: .design }
```

효과가 두 가지다.
순수 코드 PR은 체크아웃이 한 번 줄고, 확정값 저장소의 장애가 코드 판정에 영향을 주지 않는다.

다만 필요하다고 판단했는데 가져오지 못한 경우는 실패로 처리한다 (2.3절 마지막 점검 항목).
조건부로 건너뛴 것과 필요한데 실패한 것은 다르다.

두 층이 서로 다른 저장소에 있으므로 아래 두 규칙이 필요하다.
같은 저장소에 있었다면 한 커밋으로 묶여 움직여서 필요 없었을 규칙이다.

### 2.2 규칙 1: 판정 기준은 base 시점의 것을 쓴다

확정값 문서가 `infra` 레포 안에 있으므로, `infra` PR은 **판정 대상과 판정 기준을 같은 diff에 담을 수 있다.**

```
infra PR 하나에서
  - 오토스케일링 Terraform 변경
  - 확정값 문서의 오토스케일링 목표도 함께 완화

기준선 비교 결과 -> 신규 위반 없음 -> 통과
```

기준을 낮추면서 코드도 같이 낮추면 게이트를 그대로 지나간다.
qa-tradeoffs.md 6장이 요구하는 기준 조정 절차(사유와 근거 데이터 기록)도 함께 우회된다.

이를 막기 위해 판정에 쓰는 기준을 시점으로 고정한다.

| 판정 | 대상 | 기준 |
|------|------|------|
| head 판정 | head 코드 | **base 시점**의 점검 항목과 확정값 |
| 기준선 판정 | base 코드 | **base 시점**의 점검 항목과 확정값 |

PR 안에서 기준을 바꿔도 그 PR 판정에는 반영되지 않고, 병합된 뒤 다음 PR부터 적용된다.
기준 완화와 그 혜택을 한 PR에서 동시에 받는 경로가 닫힌다.

### 2.3 규칙 2: 기준 변경은 판정과 분리해 표시한다

기준 변경 자체는 막지 않는다. 정상적인 활동이고 qa-tradeoffs.md가 절차까지 정해 두었다.
다만 판정 결과에 섞이면 사람이 알아채지 못하므로 별도로 드러낸다.

diff에 다음 경로가 포함되면 판정 결과와 무관하게 리뷰 코멘트에 명시한다.

```
docs/system-design/        확정값 변경
docs/software-quality/     점검 항목 변경
```

표시 내용은 어느 항목이 어떻게 바뀌었는지와 조정 사유가 기록되었는지 여부다.

점검 항목
* `[설계]` `LLM-2-04` 판정에 쓰는 기준을 base 시점 것으로 고정하는가
* `[인프라]` `LLM-2-05` 두 기준 저장소의 참조가 모두 특정 시점으로 고정되어 있는가
* `[코드]` `LLM-2-06` 기준 문서 변경이 diff에 포함되면 별도로 표시하는가
* `[인프라]` `LLM-2-07` 기준 저장소 접근 실패 시 판정을 통과시키지 않고 실패시키는가

마지막 항목이 중요하다.
기준 저장소를 가져오지 못했을 때 조용히 건너뛰면, 판정하지 않은 PR이 통과한 것처럼 보인다.
4장의 `INSUFFICIENT_EVIDENCE`를 `OK`로 뭉뚱그리지 않는 것과 같은 이유다.

### 2.4 G-PR 재실행 규칙

PR은 한 번 열리고 끝나지 않는다. 열려 있는 동안 push가 반복되므로 재실행 규칙이 필요하다.

트리거는 세 가지다.

| 이벤트 | 시점 |
|--------|------|
| `opened` | PR 생성 |
| `synchronize` | PR이 열려 있는 상태의 매 push |
| `reopened` | 닫았다 다시 열 때 |

여기서 **증분을 어디에 적용하느냐가 핵심이다.**
비용과 소음을 줄이려고 "변경분만 검증"으로 구현하면 1.2절의 부재 판정 문제가 그대로 돌아온다.

| 범위 | 무엇을 정하는가 | 증분 적용 | 이유 |
|------|----------------|----------|------|
| 판정 범위 | 무엇을 판정 대상으로 삼는가 | **적용 안 함** | 병합되는 것은 각 push의 변경분이 아니라 PR 전체의 누적 상태다 |
| 재판정 범위 | 무엇을 LLM에 다시 물을 것인가 | 적용 | 비용 절감 |
| 출력 범위 | 무엇을 코멘트로 올릴 것인가 | 적용 | 소음 제거 (6장 기준) |

판정 범위를 좁히면 두 가지가 깨진다.
push 1에서 통과한 항목을 push 3에서 다른 파일이 무너뜨려도 재판정되지 않고, push 1의 위반을 push 2에서 고쳐도 해소가 감지되지 않아 차단이 풀리지 않는다.

```bash
# 판정 범위. push 횟수와 무관하게 항상 동일하다
git diff --name-only origin/$BASE_REF...HEAD

# 재판정 트리거. 이번 push에서 실제로 바뀐 것
git diff --name-only $BEFORE..HEAD
```

재판정 범위를 좁히려면 이전 판정을 캐시해야 하고, 캐시 키를 잘못 잡으면 판정 범위를 좁힌 것과 같은 결과가 된다.

```
캐시 키 = (항목 ID, 대상 파일 해시, 그 항목이 참조한 앵커 파일들의 해시,
          점검 항목 문서 SHA, 확정값 문서 SHA)
```

무효화는 **앵커 관계를 역방향으로 탄다.**
어떤 파일이 X의 앵커였다면, 그 파일이 바뀔 때 X는 변경되지 않았더라도 재판정 대상이다.
3장 앵커 표 기준으로 `application*.yml` 변경은 관련 항목을 거의 전부 무효화하는데, 그것이 맞는 동작이다.

점검 항목
* `[인프라]` `LLM-2-08` PR 생성과 이후 매 push에 모두 재실행되는가
* `[설계]` `LLM-2-09` 판정 범위를 이번 push의 변경분으로 좁히지 않는가
* `[코드]` `LLM-2-10` 캐시 키에 앵커 파일과 기준 문서의 해시가 포함되는가
* `[코드]` `LLM-2-11` force push로 증분 범위를 신뢰할 수 없을 때 전량 재판정으로 넘어가는가

마지막 항목은 조용히 실패하기 쉽다.
force push 후에는 이전 SHA가 조상이 아니게 되어 증분 범위 계산이 어긋나므로, 조상 여부를 검사하고 아니면 캐시를 버린다.

### 2.5 G-AUDIT 주기

`[프로세스]` 항목은 주기가 제각각이다.
하나로 뭉뚱그리면 실제로 언제 무엇을 도는지 알 수 없게 되므로, 원본 문서가 정한 주기를 그대로 따른다.

| 주기 | 대상 | 출처 |
|------|------|------|
| 1시간 | 집계값 vs 원본 합계 대조 | 데이터 정합성 7장 |
| 일 1회 | 외부 시스템 대사, 금액 대사, 상태 이력 연속성, 고아 데이터 | 데이터 정합성 7장 |
| 월 1회 | 감사 로그 검토 | 보안 5장 |
| 분기 1회 | 알림 정기 점검, 복원 리허설, 도상 훈련, 결함 유형 분포 집계, LLM 오탐 집계 | 관측 가능성 6장, 신뢰성 4장, 인시던트 10장, 기능 적합성 6장, 이 문서 6장 |
| 반기 1회 | 페일오버 훈련, 장애 주입 | 인시던트 10장 |
| 6개월 | 완화한 기준 재검토 | 트레이드오프 6장 |

위 주기는 원본 문서에 근거가 있으므로 이 표에 별도 등급 표시를 하지 않는다.
원본에서의 등급은 각 문서를 따른다.

**확정값 층이 이 주기를 덮어쓸 수 있다.**
복원 리허설이 그 사례다. 신뢰성 문서는 분기 1회 이상을 제시하지만 확정값 문서(백업과 복원 4.1절)는 **주 1회**로 정했다.
2.1절의 두 층 관계에 따라 확정값이 있으면 그쪽을 따른다. 이 표는 확정값이 없을 때의 기본값이다.

**LLM이 검사를 수행하는 것이 아니다.**
1시간과 일 1회 정합성 검사는 배치 잡의 영역이고, G-AUDIT가 하는 일은 **그 배치가 존재하고 결과가 기록되었는가**를 확인하는 것이다.
월 이상 주기의 항목도 마찬가지로 수행 기록의 존재를 본다.

이 구분이 흐려지면 7.1절의 G3와 G4를 잘못 분류하게 된다.
기록을 읽는 것은 가능하고, 그 기록이 성실했는지 판정하는 것은 불가능하다.

점검 항목
* `[프로세스]` `LLM-2-12` 주기별로 무엇이 언제 도는지 목록이 분리되어 있는가
* `[인프라]` `LLM-2-13` 각 주기의 실행 결과가 파일이나 티켓으로 남는가
* `[프로세스]` `LLM-2-14` 기한이 지났는데 기록이 없는 항목을 검출하는가

## 3. 앵커 파일 주입

1.2절의 부재 판정 문제에 대한 직접적인 대응이다.
diff만 주면 "타임아웃이 없다"를 알 수 없으므로, 판정에 필요한 파일을 함께 동봉한다.

점검 항목
* `[인프라]` `LLM-3-01` 변경 파일 유형별로 동봉할 앵커 파일이 규칙으로 정의되어 있는가
* `[설계]` `LLM-3-02` 앵커 파일이 없을 때 판정을 보류하는 경로가 있는가
* `[인프라]` `LLM-3-03` 동봉 규칙이 저장소 구조 변경에 따라 갱신되는가

앵커 규칙 (등급 C. 근거 없음. 저장소 구조에 맞게 정한다)

| 변경 파일 패턴 | 동봉할 앵커 파일 | 활성화할 문서 |
|----------------|-----------------|--------------|
| `**/*Controller.java` | SecurityConfig, 대상 Service, 응답 DTO | 보안, 호환성, 기능 적합성 |
| `**/*Repository.java`, `@Query` | 대상 엔티티, 관련 마이그레이션 SQL | 성능, 데이터 정합성 |
| `@Transactional` 포함 diff | 호출 대상 클래스, 외부 클라이언트 빈 정의 | 데이터 정합성, 신뢰성 |
| `db/migration/*.sql` | 대상 테이블 기존 DDL, 대응 엔티티 | 데이터 정합성, 호환성, 유연성 |
| `application*.yml` | 전 프로파일 yml, logback.xml, build.gradle | 성능, 신뢰성, 관측 가능성 |
| 외부 클라이언트 빈 정의 | resilience4j 설정, 타임아웃 설정 | 신뢰성 |

앵커 파일이 없으면 그 항목은 판정하지 않고 `INSUFFICIENT_EVIDENCE`로 표기한다.
추측으로 지적하면 오탐이 되고, 오탐이 쌓이면 팀이 전체를 무시하기 시작한다.
[qa-maintainability.md](./qa-maintainability.md)의 "거짓 경보가 반복되면 진짜 실패도 함께 묻힌다"가 그대로 적용된다.

## 4. 항목 ID와 출력 형식

자유 서술 리뷰를 금지한다.
LLM이 스스로 무엇을 볼지 고르게 두면, 눈에 띄는 것만 지적하고 부재 항목은 통째로 건너뛴다.

점검 항목
* `[설계]` `LLM-4-01` 모든 점검 항목에 고유 ID가 부여되어 있는가
* `[코드]` `LLM-4-02` 판정 출력이 정해진 구조를 따르는가
* `[코드]` `LLM-4-03` 증거 위치가 없는 지적을 기계적으로 폐기하는가
* `[프로세스]` `LLM-4-04` ID별로 판정 이력이 집계 가능한가

각 문서의 점검 항목에 `<문서약칭>-<장>-<순번>` 형식의 ID를 부여한다. **부여는 완료되었다.**

| 약칭 | 문서 | 항목 | 약칭 | 문서 | 항목 |
|------|------|------|------|------|------|
| `FUN` | 기능 적합성 | 17 | `DI` | 데이터 정합성 | 19 |
| `PERF` | 성능 효율성 | 18 | `OBS` | 관측 가능성 | 21 |
| `REL` | 신뢰성 | 28 | `INC` | 인시던트 대응 | 37 |
| `SEC` | 보안 | 24 | `TRD` | 트레이드오프 | 6 |
| `MNT` | 유지보수성 | 13 | `CMP` | 호환성 | 21 |
| `FLX` | 유연성과 확장성 | 13 | `LLM` | 이 문서 | 28 |

`qa-*.md` 11개 합계가 217건이고, 이 문서 자체 28건을 더하면 245건이다.

표기는 층위 뒤에 둔다.

```
  * `[코드]` `REL-2-01` 모든 외부 호출에 연결 타임아웃과 읽기 타임아웃이 설정되어 있는가
```

위 예시는 들여쓰기해 두었다. 행 첫 칸에 두면 9.1절의 집계 스크립트가 이 예시까지 실제 점검 항목으로 세어 중복으로 잡는다.

층위를 앞에 두는 이유는 두 가지다.
사람이 먼저 보는 것은 "이것이 내가 판정할 층위인가"이고, 9장의 집계 스크립트가 `^\* \`\[층위\]\`` 패턴에 의존하므로 앞자리를 바꾸면 깨진다.

**장 번호가 ID에 들어가므로 장을 재배치하면 ID가 바뀐다.**
ID는 판정 이력과 `known-conflicts.yml`이 참조하는 키이므로, 장 구조 변경은 그 참조를 함께 갱신해야 하는 작업이다.
항목을 장 안에서 추가하는 것은 안전하다. 뒤에 붙이면 기존 번호가 유지된다.

### 4.1 항목 레지스트리

문서의 ID만으로는 워크플로가 "이 항목을 언제, 어느 파일 변경에 켤 것인가"를 알 수 없다.
그 정보를 담는 레지스트리를 문서에서 추출해 생성한다.

```yaml
# .github/llm-verify/items.yml
version: 1
source: common
count: 217
items:
  - {id: DI-2-02, doc: qa-data-integrity.md, ch: 2, level: 설계, gate: G-DESIGN,
     domains: [database], title: "충돌 빈도에 맞는 잠금 방식을 골랐는가"}
```

각 필드의 출처가 다르다.

| 필드 | 출처 | 성격 |
|------|------|------|
| `id`, `doc`, `ch`, `title` | 문서에서 그대로 추출 | 기계적 |
| `level` | 층위 태그 | 기계적 |
| `gate` | 층위에서 도출 (코드->G-PR, 설계->G-DESIGN, 프로세스->G-AUDIT) | 규칙 |
| `domains` | **문서별 기본값 + 항목별 예외** | 판단 개입 |
| `gates` | 두 게이트가 모두 판정한다 (`[local, ci]`) | 규칙 |
| `ci_stage` | 소속 저장소에서 도출 (backend -> 1, 나머지 -> 2) | 규칙 |

`domains`는 기술 영역(`application`, `security`, `database`, `infra`)이며 **복수를 허용한다.**
"커넥션풀 크기"는 application이자 database이자 infra이므로 하나로 고를 수 없다.
문서 구조가 아니라 이 필드로 표현하는 이유가 그것이다. 문서로 나누면 어디 둘지 논쟁이 생기고 결국 중복되거나 누락된다.

**레지스트리는 저장소마다 자기 것을 갖는다.**

| 저장소 | 파일 | 건수 |
|--------|------|------|
| `fresh-market/.github` | `.github/llm-verify/items.yml` | 217 |
| `fresh-market/fm-backend` | `.github/llm-verify/items.yml` | 250 |

하나로 합치면 한쪽 문서가 바뀔 때마다 다른 저장소의 파일을 갱신해야 한다.
2.1절이 두 층을 각자의 저장소에 둔 것과 같은 이유이며, 워크플로가 실행 시점에 병합한다.

**backend 항목의 `level`은 아직 검증되지 않았다.**
그쪽 점검 항목에는 층위 태그가 없어 전부 `코드`로 기본 설정했고, `level_verified: false`로 표시했다.
대부분은 맞지만 "구성 선택의 근거가 기록되어 있는가" 같은 일부는 실제로 `설계`이며, 그 항목들은 G-PR이 아니라 G-DESIGN으로 가야 한다.
층위 태깅이 끝나면 이 플래그를 걷는다.

LLM은 활성화된 ID 목록을 순회하며 항목마다 다음 구조로만 답한다.

```json
{
  "id": "REL-2-01",
  "verdict": "VIOLATION",
  "evidence": "src/main/java/com/example/external/ExternalClient.java:23",
  "quote": "RestClient client = RestClient.create();",
  "reason": "연결 타임아웃과 읽기 타임아웃이 설정되지 않았다",
  "confidence": 0.9
}
```

`verdict`는 여섯 가지뿐이다.

| 값 | 의미 | 후속 처리 |
|----|------|-----------|
| `VIOLATION` | 위반 확인 | 코멘트로 보고. 병합은 막지 않는다 |
| `OK` | 충족 확인 | 기록만 |
| `NOT_APPLICABLE` | 이 변경과 무관 | 기록만 |
| `INSUFFICIENT_EVIDENCE` | 판정에 필요한 증거가 입력에 없음 | 앵커 규칙 보강 대상 |
| `CONFLICTING_BASELINE` | 확정값이 문서마다 다르다 | 양쪽 값을 함께 표기해 결정을 요청 |
| `UNJUDGED` | **판정되지 않았다** | 미판정 목록에 기록. 8장 지표로 집계 |

앞의 다섯은 LLM이 답한다. **`UNJUDGED`는 LLM이 만들지 않는다.**
요청한 ID 중 응답에 없는 것을 실행 측이 채워 넣는 값이며, 2단계를 건너뛴 경우도 여기 들어간다.
이 값이 없으면 물어보지 않은 항목과 통과한 항목이 구분되지 않는다.

마지막 값은 7.2절의 상태를 다루기 위한 것이다.
확정값 문서 사이에 모순이 남아 있으면 어느 쪽으로도 판정할 수 없고, 한쪽을 임의로 골라 판정하면 **LLM이 팀의 결정을 대신 내리는 셈**이 된다.

이때 차단하지 않는 이유는, 모순의 원인이 이번 PR이 아니기 때문이다.
남의 부채로 남의 PR을 막으면 2장에서 경계한 우회 문화가 생긴다.
출력에는 어느 문서가 무엇을 말하는지를 함께 실어, 판정 대신 **결정을 요청하는 형태**로 남긴다.

```json
{
  "id": "REL-5-01",
  "verdict": "CONFLICTING_BASELINE",
  "evidence": "fresh-market/fm-infra docs/system-design/백엔드공통_앱과DB_장애대응구조.md:25",
  "conflict": [
    { "source": "앱과DB 4.1절", "value": "공유 의존성 제외" },
    { "source": "기술스택 4.2절", "value": "include: db, diskSpace" }
  ],
  "confidence": 1.0
}
```

이 구조가 세 가지를 동시에 해결한다.
부재 판정을 명시적 질문으로 바꾸어 재현율을 올리고, `evidence`가 없는 지적을 폐기해 환각을 억제하며, ID 단위 집계로 항목별 정확도 측정이 가능해진다.
마지막 것이 6장의 전제다.

`INSUFFICIENT_EVIDENCE`를 별도 값으로 둔 것이 중요하다.
이것을 `OK`로 뭉뚱그리면 "판정하지 못했다"가 "문제없다"로 둔갑한다.

## 5. 역할 분할

점검 항목
* `[설계]` `LLM-5-01` 결정론적 도구가 판정할 수 있는 항목을 LLM에게 주지 않는가
* `[설계]` `LLM-5-02` LLM이 값이 아니라 구조를 판정하도록 항목이 서술되어 있는가
* `[프로세스]` `LLM-5-03` 사람만 판단할 수 있는 항목이 명시적으로 분리되어 있는가

| 주체 | 담당 | 원칙 |
|------|------|------|
| 결정론적 도구 | Checkstyle, SpotBugs, ArchUnit, SAST, EXPLAIN, 마이그레이션 린터 | 기계가 잡을 수 있는 것은 LLM에게 주지 않는다 |
| LLM 판정자 | 의미 판단이 필요한 것. 이름과 부수 효과의 불일치, 대체 동작의 안전성, 소유권 검증 누락, 호환 파괴 여부 | 값이 아니라 구조를 판정한다 |
| LLM 작성자 | ADR 초안, 런북 초안, 사후 분석 초안, 정합성 검사 쿼리 초안 | 판정하지 않는다. 사람의 입력 비용만 낮춘다 |
| 사람 | 등급 C 수치의 확정, 트레이드오프 선택, 완화 판단 | 위임 불가 |

[qa-maintainability.md](./qa-maintainability.md)는 "포맷터와 정적 분석 도구가 기계적으로 처리하면 사람은 도구가 못 잡는 설계와 로직에 집중할 수 있다"고 적었다.
LLM은 그 도구와 사람 사이의 빈칸만 맡는다.
ArchUnit이 이미 잡는 순환 참조를 LLM이 또 지적하면 같은 내용이 두 번 올라와 소음만 늘어난다.

## 6. 오탐 관리

[qa-observability.md](./qa-observability.md)의 알림 정기 점검 절차를 그대로 옮긴다.
LLM 리뷰도 알림과 같은 성질을 갖는다. 늘어나기만 하고 줄지 않으며, 정확도가 떨어지면 전체가 무시된다.

점검 항목
* `[프로세스]` `LLM-6-01` LLM 지적의 항목별 정확도를 정기적으로 집계하는가
* `[프로세스]` `LLM-6-02` 정확도가 낮은 항목을 제거하거나 보강하는 절차가 있는가
* `[프로세스]` `LLM-6-03` 한 번도 발화하지 않은 항목을 확인하는가
* `[설계]` `LLM-6-04` 차단 대상 항목이 정확도 기준을 충족하는가

```
분기 1회 수행

1. 지난 분기 LLM 지적 전수를 항목 ID별로 집계
2. ID별로 판정
   - 실제 수정으로 이어졌는가 (Y/N)
   - INSUFFICIENT_EVIDENCE 비율은 얼마인가
3. 정확도 30% 미만 항목 -> 프롬프트에서 제거하거나 앵커 파일 보강
4. 한 번도 발화하지 않은 항목 -> 트리거 조건이 잘못됐는지 확인
5. 사고는 났는데 지적이 없었던 구간 -> 항목 추가
6. 결과와 변경 내역 기록
```

판정 기준 (등급 C. 근거 없음. 3개월 측정 후 확정한다)

| 항목 | 예시값 | 정한 이유 |
|------|--------|-----------|
| 차단 전환 최소 정확도 | 90% | 현재는 전부 비차단이다. 이 값을 넘긴 항목만 차단 후보가 된다 |
| 항목 유지 최소 정확도 | 30% | 미달 시 제거 대상 |
| PR당 지적 건수 | 10건 이하 | 초과 시 읽히지 않는다 |
| `INSUFFICIENT_EVIDENCE` 비율 | 20% 이하 | 초과는 앵커 규칙 결함 |

판정하지 못하는 항목을 목록에 남겨 두면 나머지 항목의 신뢰도까지 떨어진다.
[qa-tradeoffs.md](./qa-tradeoffs.md)의 "지켜지지 않는 기준은 삭제한다"가 여기에도 적용된다.

## 7. 커버리지 계산

이 설계로 217건 중 몇 건을 실제로 판정할 수 있는지 계산한다.

이 장의 분류는 초판에서 한 차례 전면 개정되었다.
초판은 확정값 문서(`fresh-market/fm-infra`의 `docs/system-design/`, 9개 문서 5,706줄)의 **존재를 모른 채** 작성되었고, ADR이 아직 없다는 전제로 계산했다.
실제로는 ADR 34건(INF-01~34)을 포함한 확정값 층이 이미 있었다.
7.2절이 그 실제 상태를, 7.3절 이후가 그것을 반영한 수치를 담는다.

### 7.1 항목별 판정 가능 등급

초판의 4등급으로는 실제 상태를 표현할 수 없어 5등급으로 나눈다.
초판의 G3(조건부)이 두 갈래로 갈리기 때문이다. 확정값이 실제로 적혀 있는 항목과, 문서는 있으나 값이 아직 비어 있거나 문서끼리 어긋나는 항목은 판정 가능성이 전혀 다르다.

| 등급 | 정의 | 판정 |
|------|------|------|
| G1 | 결정론적 도구가 판정 (SonarQube, JaCoCo) | 가능 |
| G2 | LLM 단독 판정. 증거가 코드 저장소에 완결 | 가능 |
| G3 | 확정값 문서를 참조해 판정. **확정값이 실제로 존재** | 가능 |
| G4 | 확정값이 미정이거나 문서 간 모순 | **현재 불가** |
| G5 | 구조적 판정 불가 (사람의 행위, 실측, 미래 예측) | 불가 |

분류 결과 (등급 C. 항목별 분류는 판단이 개입하므로 팀이 재검토한다)

| | 총계 | G1 | G2 | G3 | G4 | G5 |
|------|------|----|----|----|----|----|
| 합계 | 217 | 17 | 89 | 42 | 18 | 51 |

> **층위별 내역은 싣지 않는다.**
> G1~G5 분류는 항목마다 손으로 매긴 것인데, 2026-08-07 에 층위 태그 32건을 정정하면서
> 항목이 층위 사이를 옮겨 다녔다. 항목 자체는 그대로이므로 **합계 행은 지금도 맞지만**,
> 층위별로 쪼갠 수치는 옛 태그 기준이라 지웠다.
> 다시 필요하면 항목별 G1~G5 분류부터 새로 매겨야 한다.

초판 대비 두 방향으로 움직였다.

**G1이 23건에서 17건으로 줄었다.** 초판은 Checkstyle, SpotBugs, ArchUnit이 있다고 가정했으나, 확정 스택(기술 스택 문서 2.2절과 2.5절)에 그 셋이 없다.
정적 분석은 SonarQube Cloud, 커버리지는 JaCoCo 하나씩이다.
특히 **ArchUnit이 없어 도메인 경계와 순환 참조 판정이 도구에서 빠졌고**, 그만큼이 G2로 넘어와 LLM 부담이 늘었다.

**초판의 G3 61건이 G3와 G4로 갈렸다.** 확정값 문서가 있다고 모든 값이 정해진 것은 아니다.

**소유권 재배분으로 6건이 backend 저장소로 이관되었다.** 도메인 경계 3건(`MNT-1-*`), 테스트 실행 시간 1건, 페이지네이션 1건, 그리고 common 내부 중복이던 checked 예외 롤백 1건이다.
이관된 항목은 사라진 것이 아니라 `fresh-market/fm-backend`의 `docs/code-architecture/`가 판정한다.

### 7.2 확정값 문서의 실제 상태

판정에 쓸 수 있는지는 확정값이 **적혀 있는가**로 갈린다. 세 부류가 섞여 있다.

#### 채워진 것

qa 문서가 등급 C로 비워 둔 자리를 확정값 문서가 실제로 채운 사례다.

| 점검 항목이 요구하는 것 | qa 문서의 등급 C 예시값 | 확정값 |
|------------------------|------------------------|--------|
| 가용성 목표 | 기능 등급별 99.5~99.95% | 장애 시나리오 9종별 RTO와 RPO, 보장 메커니즘까지 |
| 타임아웃 예산 | 게이트웨이 10s, 서비스 간 1s/5s | 종료 4계층(30/30/45/60초)과 요청 4계층(3/5/10/60초) |
| 커넥션풀 | `(DB 코어 x 2) + 디스크` | `maximum-pool-size: 10`, `minimum-idle: 10`, 인스턴스 수별 총량표 |
| 헬스체크 분리 | "liveness가 외부 의존성에 좌우되지 않는가" | liveness는 Docker, readiness는 ALB. 경로와 임계값까지 |
| 추적 샘플링 | 오류 100%, 핵심 10%, 일반 1% | 평상시 10%, 부하 시험 5%, 장애 주입 100%, 오류 100% |
| 복원 리허설 주기 | 분기 1회 이상 | **주 1회** (qa 기준보다 엄격) |
| 테스트 커버리지 | "목표로 삼지 않는다" | **service 패키지 메서드 100%, 미달 시 병합 차단** |
| 정적 분석 | 경고 0 | SonarQube 신규 Blocker 0건 차단, 브랜치 보호로 강제 |
| 스키마 변경 | 4단계 확장 후 축소 | 동일 + 금지 DDL 4종 명시 + CI 차단 |
| 배포 롤백 | 예시 없음 | 롤백 트리거 5종과 각각의 동작 |

**복원 리허설과 커버리지 두 행이 중요하다.**
확정값 층이 qa 문서보다 **더 엄격한** 기준을 정한 사례이며, 확정값 층이 단순히 빈칸을 메우는 것이 아니라 판정 기준을 실제로 대체한다는 것을 보여 준다.

#### 아직 비어 있는 것

| 항목 | 상태 | 출처 |
|------|------|------|
| 알람 임계값 5곳 | `(미정)` 표기 | 알람과 알림 10.1절 |
| 오토스케일링 임계값 9항목 | 전부 `(미정)` | 오토스케일링 8절 |
| RDS `max_connections` | 미실측. 풀 크기와 인스턴스 상한의 전제 | 여러 문서 |
| PITR 실측 RTO, RPO | "근거 없는 목표치" 라고 문서가 명시 | 백업과 복원 4.2절 |
| 설정값 5종 | socketTimeout, 풀 크기, 트랜잭션 타임아웃, 톰캣 스레드, ALB 임계값 | 시스템 디자인 종합 13절 |
| QueryDSL 채택 | 미확정. 착수 전 스파이크 필요 | 기술 스택 3.8절 |

이 항목들에 걸린 점검 항목은 **근거 판정(기록이 있는가)은 가능하고 일치 판정(값이 같은가)은 불가능하다.**
"측정 전에는 경보 없이 관측만" 이라는 규율을 그대로 적용해 G4로 둔다.

#### 서로 어긋나는 것

같은 사실이 문서마다 다르게 적혀 있으면 판정 기준이 둘이 되어 어느 쪽으로도 판정할 수 없다.

| 항목 | 한쪽 | 다른 쪽 |
|------|------|---------|
| readiness 포함 대상 | 앱과 DB 장애 대응 1.1절: db 포함은 **잘못이며 철회**. 공유 의존성 제외 | 기술 스택 4.2절: `readiness: include: db, diskSpace` |
| 배포 중 용량 | 장애 대응 목표 7.1절: 50% | 무중단 배포 1절, 시스템 디자인 종합 7절: 100% |
| 배포 소요 | 장애 대응 목표 7.1절: 3~4분 | 무중단 배포 1절: 6~8분 |
| 혼재 구간 | 장애 대응 목표 7.1절: 약 2분, 7.4절: 약 3분 | 무중단 배포 8절: 약 1분 |

첫 행이 가장 위험하다.
철회된 설계가 다른 문서에 살아남아 있고, 그 문서가 **실행 가능한 yaml 형태**라 그대로 복사될 가능성이 높다.
공유 의존성을 readiness에 넣으면 DB 장애 시 전 인스턴스가 동시에 대상 그룹에서 빠지는데, 이는 두 문서가 공통으로 경계한 바로 그 실패 양상이다.

세 번째와 네 번째 행은 같은 문서 안에서도 어긋난다.
시스템 디자인 종합 7절 표는 혼재 1분인데 7.2절 본문은 2분이고, 7절 표는 용량 100%인데 7.3절 본문은 "용량이 절반이 되는데"다.

**이 유형은 LLM이 발견하기 좋은 결함이다.** 문서 전체를 한 번에 읽고 대조하는 작업이라 사람이 놓치기 쉽고 기계적으로 확인 가능하다.
G-AUDIT의 분기 항목으로 "확정값 문서 간 상호 모순 검출"을 두는 것이 실효가 있다.

#### 모순을 고치지 않고 운영하는 경우

확정값 문서 수정은 보류된 상태다. 따라서 게이트는 모순이 남아 있는 채로 돌아간다.

해당 항목은 4장의 `CONFLICTING_BASELINE`으로 처리하고 차단하지 않는다.
한쪽을 임의로 골라 판정하면 LLM이 팀의 결정을 대신 내리는 것이 되고, 차단하면 모순과 무관한 PR이 막힌다.

알려진 모순은 **목록으로 관리한다.** 목록에 없으면 새로 발견된 것이므로 보고하고, 목록에 있으면 매 PR마다 다시 지적하지 않는다.
이것이 없으면 같은 지적이 모든 PR에 반복되어 6장이 경계한 소음이 된다.

```
.github/llm-verify/known-conflicts.yml

- id: REL-5-01
  topic: readiness 포함 대상
  sources:
    - { doc: 앱과DB 4.1절, value: 공유 의존성 제외 }
    - { doc: 기술스택 4.2절, value: "include: db, diskSpace" }
  status: unresolved
```

목록에 `status`를 두는 이유는, 해소되지 않은 항목이 조용히 쌓이는 것을 막기 위해서다.
분기 점검(6장)에서 이 목록의 길이와 각 항목의 경과 기간을 함께 본다.

#### 모순과 구분해야 하는 것: 의도된 이탈

점검 항목 층과 확정값 층이 다른 말을 하는 경우가 있다. **이것은 모순이 아니다.**

| 주제 | 점검 항목 층 (일반론) | 확정값 층 (이 팀의 결정) |
|------|----------------------|------------------------|
| readiness 구성 | 신뢰성 5장: "의존성 상태는 readiness에서 본다" | 공유 의존성을 readiness에서 제외 (INF-16, 되돌릴 수 없음) |

2.1절의 두 층 관계에 따라 확정값이 이긴다.
확정값 문서가 이유를 명시했고(공유 의존성 장애 시 전 인스턴스가 동시에 대상 그룹에서 빠져 상황이 악화됨) ADR에 되돌릴 수 없는 결정으로 기록했기 때문이다.

**이런 항목은 고칠 대상이 아니라 기록할 대상이다.**
기록해 두지 않으면 나중에 점검 항목 문서를 근거로 "확정값이 틀렸다"며 되돌리는 일이 생긴다.
`known-conflicts.yml`에 `status: intentional`로 남겨 재발견과 재논의를 막는다.

### 7.3 재현율 할인

판정할 수 있다는 것과 매번 잡아낸다는 것은 다르다.

아래 재현율은 **전부 등급 C이며 근거가 없다.**
도입 후 3개월간 실측해 확정해야 한다. 측정 전에는 차단 없이 관측만 하는 상태로 둔다.

**재현율은 판정 모델에 종속된다.** G-LOCAL 과 G-PR 이 다른 모델을 쓰므로 값도 따로 측정한다.
아래 표는 모델을 구분하기 전에 정한 값이라 실측 시 두 벌로 갈라진다.
어느 모델로 측정했는지를 함께 기록하지 않으면 모델을 바꿨을 때 옛 수치가 그대로 인용된다.

| 판정 유형 | 가정 재현율 | 근거 |
|-----------|------------|------|
| G1 결정론적 도구 | 0.98 | 규칙 기반이라 누락이 거의 없다 |
| G2 부정형 (있는 것 지적) | 0.85 | 안티패턴이 diff에 그대로 보인다 |
| G2 긍정형 (없는 것 지적) | 0.75 | 3장 앵커 주입과 4장 ID 순회 적용 시 |
| G3 확정값 대조 | 0.80 | 대조 대상이 명확하나 문서를 가로질러 찾아야 한다 |

G2 89건의 내부 구성은 부정형 약 27건, 긍정형 약 62건이다.

```
G1        : 17 × 0.98 = 16.7
G2 부정형 : 27 × 0.85 = 23.0
G2 긍정형 : 62 × 0.75 = 46.5
G3        : 42 × 0.80 = 33.6
                        ------
                        119.8건
```

### 7.4 결론

| 구분 | 건수 | 비율 |
|------|------|------|
| 판정 가능 (G1+G2+G3) | 148 | 68.2% |
| 재현율 반영 실효 커버리지 | 120 | **55.2%** |
| 확정 대기 (G4) | 18 | 8.3% |
| 구조적 불가 (G5) | 51 | 23.5% |

**현재 실효 커버리지는 약 55%다.**
분모가 223에서 217로 줄었지만 비율은 거의 그대로다. 이관된 6건이 대부분 판정 가능한 항목(G2)이었기 때문이다.

초판이 제시한 41%(현재)와 64%(산출물 정비 후) 사이에 들어온다. 이유는 두 가지가 상쇄되었기 때문이다.

| 방향 | 사유 | 영향 |
|------|------|------|
| 상승 | ADR과 확정값이 이미 존재하고 저장소에 있다. 초판이 "앞으로 만들어야 한다"고 본 것이 이미 있었다 | +약 15%p |
| 하락 | 확정 스택에 Checkstyle, SpotBugs, ArchUnit이 없어 G1이 축소. 미정과 모순으로 G4 18건 발생 | -약 8%p |

#### 이 수치가 능력치이지 현황이 아니라는 점

**`fresh-market/fm-backend` 저장소에는 현재 `README.md` 하나뿐이다.**
소스 코드도 `application.yml`도 없다. 즉 지금 게이트를 돌리면 판정 대상이 0건이다.

55%는 "코드가 있을 때 217건 중 몇 건을 판정할 수 있는가"이지 "지금 몇 건이 지켜지고 있는가"가 아니다.
`[인프라]` G2 25건이 특히 그렇다. 타임아웃, 커넥션풀, 헬스체크 설정은 확정값 문서에 완전한 yaml로 적혀 있지만 **아직 코드 저장소에 옮겨지지 않았다.**

### 7.5 커버리지를 올리는 방법

초판은 "ADR을 `docs/adr/`에 쌓는 것이 첫 번째 조치"라고 적었다. **그 전제는 틀렸다.**
ADR은 이미 34건이 있고 `fresh-market/fm-infra`의 `docs/system-design/`에 있다. 만드는 작업이 아니라 이미 있는 것을 쓰는 작업이다.

남은 지렛대는 다음 셋이다.

| 조치 | 회복되는 항목 | 성격 | 상태 |
|------|--------------|------|------|
| 미정 값을 부하 시험으로 확정 | G4 중 14건 | 측정 작업. 오토스케일링과 알람 임계 | 부하 시험 대기 |
| 확정값 문서 간 모순 해소 | G4 중 4건 | 문서 정리. readiness 항목이 최우선 | **보류** |
| 도구 스택 보강 (ArchUnit 등) | G2 중 6건이 G1로 이동 | 재현율 0.75에서 0.98로 상승 | 미착수 |

첫 두 조치로 G4 18건이 전부 G3로 올라가면 판정 가능이 166건(76.5%), 실효는 약 134건(61.7%)이 된다.

**두 번째 조치는 현재 보류되어 있다.** 확정값 문서를 수정하지 않는 방침이므로 해당 4건은 G4에 남고, 7.2절의 `CONFLICTING_BASELINE` 경로로 처리한다.
보류 자체는 문제가 아니지만, 보류가 길어지면 판정하지 못하는 항목이 고착된다.
6장의 분기 점검에서 `known-conflicts.yml`의 경과 기간을 함께 보는 이유가 이것이다.

세 번째는 커버리지 항목 수를 늘리지는 않고 재현율만 올린다.
도메인 경계와 순환 참조는 ArchUnit이 확실하게 잡는 영역이라 LLM에 맡기는 것이 비효율적이다.

### 7.6 회복되지 않는 24%

G5 51건은 어떤 설계로도 회복되지 않는다.
인시던트 대응 문서의 훈련, 역할 분리, 비난 없는 문화는 사람이 실제로 하는 행위이고, LLM은 그 행위의 **기록 유무**까지만 볼 수 있다.
기록이 있다는 것과 훈련이 실제로 유효했다는 것은 다르다.

이 구간까지 커버한다고 주장하는 설계는 검증이 아니라 검증 시늉을 자동화하는 것이다.

또한 55%는 **항목 커버리지이지 결함 커버리지가 아니다.**
G5로 빠진 인시던트 대응 항목들은 건수로는 24%지만, 사고 발생 시 손실 규모로 보면 비중이 훨씬 크다.
이 설계는 사고의 24%를 방치하는 것이 아니라, 사람이 반드시 봐야 할 24%를 명시적으로 남겨 두는 것으로 이해해야 한다.

## 8. 측정 지표

| 지표 | 의미 | 기준 (등급 C) |
|------|------|---------------|
| 항목 커버리지 | 판정 시도된 항목 / 전체 217건 | 도입 6개월 내 55% (7.4절) |
| 지적 정확도 | 실제 수정으로 이어진 지적 비율 | 전체 70%. 90% 이상이면 차단 후보 |
| `INSUFFICIENT_EVIDENCE` 비율 | 앵커 규칙의 충실도 | 20% 이하 |
| 유출 결함 중 점검 항목 해당분 | 게이트를 통과했으나 사고로 이어진 건 | 추세 감소 |
| PR당 지적 건수 | 읽히는 양인가 | 10건 이하 |
| 지적 무시율 | 수정도 응답도 없이 병합된 지적 비율 | 30% 이하. 초과하면 항목을 줄인다 |

가장 중요한 것은 네 번째 지표다.
게이트를 통과했는데 사고가 났다면, 그 항목의 재현율 가정이 틀렸다는 뜻이다.
7.2절의 등급 C 수치를 갱신하는 근거로 쓴다.

정확도만 보면 지적을 줄이는 방향으로 최적화된다.
재현율을 함께 보지 않으면 "아무것도 지적하지 않는 정확한 리뷰어"가 된다.

## 9. 집계 재현 방법

1장의 등급 A 수치는 다음으로 재현한다.

```bash
# docs/software-quality 에서 실행한다
# 이 문서 자신의 점검 항목은 집계 대상이 아니므로 제외한다
EX=--exclude=qa-llm-verification.md

for lv in 코드 설계 인프라 프로세스; do
  n=$(grep -h $EX "^\* \`\[$lv\]\`" qa-*.md | wc -l | tr -d ' ')
  neg=$(grep -h $EX "^\* \`\[$lv\]\`" qa-*.md | grep -c '않는가\|없는가')
  echo "$lv: 총 $n / 부정형 $neg / 긍정형 $((n-neg))"
done

echo "합계: $(grep -h $EX '^\* `\[' qa-*.md | wc -l | tr -d ' ')건"
```

```
코드: 총 65 / 부정형 21 / 긍정형 44
설계: 총 65 / 부정형 3 / 긍정형 62
인프라: 총 42 / 부정형 3 / 긍정형 39
프로세스: 총 51 / 부정형 5 / 긍정형 46
합계: 217건
```

제외 지정을 빠뜨리면 이 문서의 점검 항목 28건이 섞여 집계가 245건이 된다.

### 9.0 세 저장소의 점검 항목 총계

점검 항목은 세 저장소에 나뉘어 있고 각자 레지스트리를 갖는다 (4.1절).

| 저장소 | 건수 | 다루는 것 |
|--------|------|-----------|
| `fresh-market/.github` | 217 | 일반 품질 속성. "얼마나 잘 하는가" |
| `fresh-market/fm-backend` | 250 | 코드 관용과 패턴. "어떻게 쓰는가" |
| `fresh-market/fm-infra` | 100 | 인프라 결정이 코드에 부과하는 제약 |
| 합계 | **567** | |

7장의 커버리지 계산은 `.github`의 217건만을 분모로 한다.
나머지 350건은 소유 정리를 마친 시점이 달라 아직 G1~G5 분류에 포함되지 않았다.
**7장의 55%와 9.2절의 활성화 비율은 다른 것을 재는 수치다.**

### 9.1 항목 ID 검증

ID는 판정 이력의 키이므로 중복이나 결번이 있으면 이력이 어긋난다.

**추출 대상을 점검 항목 줄로 한정해야 한다.** 본문에서 ID를 인용한 곳까지 세면 인용이 중복으로 잡힌다.

```bash
ids() { grep -h '^\* `\[' qa-*.md | grep -o '`[A-Z]\+-[0-9]\+-[0-9]\+`' | tr -d '`'; }

# 1. 중복 검출
ids | sort | uniq -d

# 2. 장별 결번 검출
ids | sort -t- -k1,1 -k2,2n -k3,3n | awk -F- '
  { key = $1 "-" $2
    if (key != prev) { prev = key; expect = 1 }
    if ($3 + 0 != expect) print "결번: " $0 " (기대 " expect ")"
    expect++ }'

# 3. ID 없는 점검 항목 검출
grep -n '^\* `\[' qa-*.md | grep -v '`[A-Z]\+-[0-9]\+-[0-9]\+`'

# 4. 본문 인용이 실재하는 ID인지 확인
comm -23 <(grep -hov '^\* `\[' qa-*.md | grep -o '`[A-Z]\+-[0-9]\+-[0-9]\+`' | tr -d '`' | sort -u) <(ids | sort -u)
```

네 명령 모두 출력이 없어야 정상이다.

4번이 중요하다. 본문에서 예시로 든 ID가 실재하지 않거나 다른 항목을 가리키면 문서가 스스로 어긋난다.
실제로 초판은 readiness 모순의 ID를 `REL-5-04`로 적었는데 그 번호는 liveness 항목이었고, 이 검증으로 발견해 `REL-5-01`로 정정했다.

점검 항목을 추가하거나 옮기면 수치가 달라진다.
7장의 커버리지도 함께 재계산해야 한다. 갱신하지 않으면 오래된 비율이 근거처럼 인용된다.

### 9.2 앵커 활성화 커버리지

앵커 규칙이 567건 중 몇 건을 실제로 켜는지 확인한다.
규칙에서 빠진 항목은 **조용히 판정되지 않으므로**, 미포함이 의도된 것인지 누락인지 매번 대조해야 한다.

```bash
# 세 저장소가 나란히 클론된 작업 폴더에서 실행한다
python3 - <<'EOF'
import yaml, collections
items = []
for repo in ["common", "backend", "infra"]:
    items += yaml.safe_load(open(f"{repo}/.github/llm-verify/items.yml"))["items"]
by = collections.defaultdict(list)
for it in items:
    by[it["id"].rsplit("-", 2)[0]].append(it)

a = yaml.safe_load(open("backend/.github/llm-verify/anchors.yml"))
covered = set()
for r in a["rules"]:
    act = r["activate"]
    levels = set(act.get("levels", []))
    chapters = act.get("chapters", {}) or {}
    for pre in act.get("prefixes", []):
        allow = chapters.get(pre)
        for it in by.get(pre, []):
            if levels and it["level"] not in levels:
                continue
            if allow is not None and it["ch"] not in allow:
                continue
            covered.add(it["id"])

unc = [it for it in items if it["id"] not in covered]
print(f"전체 {len(items)} / 활성화 {len(covered)} / 미포함 {len(unc)}")
print("미포함 게이트:", dict(collections.Counter(i["gate"] for i in unc)))
EOF
```

기대 출력

```
전체 567 / 활성화 464 / 미포함 103
미포함 게이트: {'G-AUDIT': 77, 'G-RELEASE': 13, 'G-PR': 9, 'G-DESIGN': 4}
```

미포함 103건의 내역은 다음과 같고 **전부 의도된 것**이다.

| 게이트 | 건수 | 내용 | 판정 주체 |
|--------|------|------|-----------|
| G-AUDIT | 77 | 프로세스 항목. 인시던트 대응 37건, infra의 도입 판정과 검증 계획 34건 | 주기별 감사 |
| G-RELEASE | 13 | infra의 실행 전 점검(`PRE-*`). RDS 상태, 크레딧 잔량 | 배포와 시험 스크립트 |
| G-PR | 8 | 인시던트 대응의 인프라 항목. 분산 락 만료, 트래픽 단계 유입 | infra의 anchors.yml (미작성) |
| G-DESIGN | 5 | split brain 방어, 캐시 웜업 | 동일 |

마지막 두 줄 13건이 **유일하게 열려 있는 구멍**이다. 10장 2번 항목에 기록했다.

**항목을 추가하거나 규칙을 고치면 이 절의 기대 출력을 함께 갱신한다.** 갱신하지 않으면 오래된 비율이 근거처럼 인용된다.

## 10. 남은 작업과 막힌 지점

지금까지 만든 것은 전부 **데이터**다. 판정 기준, 항목 레지스트리, 앵커 규칙이 있고 **실행 코드는 없다.**

아래는 남은 작업과 각각이 무엇에 막혀 있는지다. 막힌 이유가 없는 것부터 한다.

### 10.1 지금 할 수 있는 것

| 작업 | 산출물 | 비고 |
|------|--------|------|
| 워크플로 본체 골격 | `fresh-market/.github`의 `.github/workflows/llm-verify.yml` | 실행은 못 해도 데이터가 실제로 맞물리는지는 짜 봐야 드러난다 |
| 호출자 워크플로 | 각 저장소 `.github/workflows/` 3줄 | 본체를 `uses:`로 부른다 |
| `known-conflicts.yml` | 7.2절의 확정값 모순 4건 등록 | 모순 해소가 보류된 상태이므로 목록이 필요하다 |
| backend 항목의 층위 태깅 | 250건에 `[코드]`/`[설계]`/`[인프라]` 부여 | 지금은 전부 `코드`로 기본 설정되어 `level_verified: false`다 |

### 10.2 코드가 생겨야 하는 것

| 작업 | 막힌 이유 | 해소 조건 |
|------|-----------|-----------|
| **재현율 5개 실측** | 판정 대상 코드가 없다. `fresh-market/fm-backend`에 문서와 README뿐이다 | PR 20~30건을 돌리면 항목별 재현율 분포가 나온다 |
| **첫 판정 비용 결정** | 동일 | `controller` 규칙이 214건을 켠다. 항목별 `NOT_APPLICABLE` 비율을 보면 좁힐 범위가 정해진다 |
| **차단 임계 결정** | 측정 이력이 없다 | 6장 기준은 "정확도 90% 이상만 차단"이다. 초기에는 전부 비차단으로 시작한다 |
| **사고 토큰 규모 측정** | `gemini-2.5-flash` 는 thinking 토큰이 출력에 산입된다 | 첫 실행에서 측정. 과하면 thinking budget 을 조정 |

### 10.3 다른 산출물을 기다리는 것

| 작업 | 막힌 이유 | 해소 조건 |
|------|-----------|-----------|
| **infra의 `anchors.yml`** | Terraform 파일 구조가 확정되지 않았다. `trigger` glob을 채울 수 없다 | backend가 `domain-package-boundary-guideline.md`로 패키지 구조를 확정한 것과 같은 방식. 또는 Terraform을 실제로 작성 |
| G4 18건 해소 | 확정값이 미정이거나 문서 간 모순이다 (7.2절) | 부하 시험 실측 14건, 문서 정리 4건 |
| ADR 축적 | 저장소별 국소 결정 기록이 아직 없다 | `docs/adr/` 신설 |

### 10.4 결정이 필요한 것

| 항목 | 선택지 |
|------|--------|
| `GEMINI_API_KEY` 보관 위치 | org 시크릿 또는 저장소별. 공개 저장소라 fork PR에는 전달되지 않는다 |
| G-LOCAL 결과를 커밋에 남길지 | 남기면 G-PR 이 실행 여부를 확인할 수 있다. 안 남기면 로컬 단계가 사실상 선택이 된다 |
| fork PR 처리 | 게이트를 건너뛰고 라벨로 표시. `pull_request_target`은 쓰지 않는다 |
| 확정값 문서 모순 해소 | 현재 보류. 보류가 길어지면 판정 불가 항목이 고착된다 (7.5절) |
| 분산 락 항목의 소속 | 현재 infra. 판단 기준은 "어느 결정에서 파생됐는가"로 확정했다 |

### 10.5 판정 모델과 호출 단위

**두 게이트가 다른 모델을 쓴다** (2.0절).

| 게이트 | 모델 | 시크릿 |
|--------|------|--------|
| G-LOCAL | 개발자가 쓰는 CLI 에이전트 (로컬) | 없음. API 를 부르지 않는다 |
| G-PR | `gemini-2.5-flash` (무료 등급) | `GEMINI_API_KEY` |

#### 호출 단위는 전체 1회로 확정한다

4장이 "ID 목록을 순회한다"고만 적고 호출 단위를 규정하지 않았다.
무료 등급의 제약 셋이 **같은 결론을 가리키므로** 이 값은 등급 C가 아니다.

| 제약 | 값 | 함의 |
|------|-----|------|
| RPM | 10 | 항목당 1회(214회)면 21분이 걸린다. 불가 |
| TPM | 250,000 | 배치 분할 시 diff와 앵커가 매번 재전송된다 |
| **컨텍스트 캐싱** | **무료 등급 사용 불가** | 재전송을 줄일 수단이 없다 |
| 컨텍스트 창 | 1M | 전체 1회가 물리적으로 가능하다 |

```
앵커 포함 입력이 20K 토큰일 때

  전체 1회    20K            TPM 의 8%
  배치 11회   20K x 11 = 220K   TPM 의 88%   <- 순손실
```

**배치 분할은 얻는 것 없이 TPM만 소모한다.** 캐싱이 그 비용을 줄이는 유일한 수단이었는데 무료 등급에서 쓸 수 없다.

입력과 출력 모두 무료 등급에서 과금이 없으므로 **프롬프트를 크게 만드는 것에 비용 부담이 없다.**
앵커 파일을 넉넉히 동봉하는 3장 설계가 그대로 유효하다.

#### 그라운딩은 끈다

Google 검색 그라운딩이 500 RPD까지 무료지만 쓰지 않는다.
backend `CODEREVIEW.md`의 봇 규칙 4번과 정면으로 충돌하기 때문이다.

> 봇은 외부 링크를 가져오지 않으며, 가이드 본문에 적힌 내용만으로 판단한다.

그라운딩을 켜면 같은 diff에 대한 판정이 검색 결과에 따라 달라져 **재현이 불가능해진다.**

#### 남은 미지수

`gemini-2.5-flash`는 thinking 토큰이 출력에 산입된다.
214건을 한 번에 판정하면 판정 결과 자체는 약 17K 토큰이지만 사고 토큰이 얼마나 붙는지는 알 수 없다.
무료라 비용 문제는 없으나 **출력 상한과 TPM에는 함께 잡히므로** 첫 실행에서 측정한다.

### 10.6 이 목록을 갱신하는 시점

작업을 마치면 해당 줄을 지우고, 그 작업이 만든 새 제약을 추가한다.
**해소된 항목을 남겨 두면 목록이 현재 상태를 반영하지 못해 아무도 보지 않게 된다.**
6장이 "무시되는 알림이 쌓이지 않는가"를 묻는 것과 같은 이유다.
